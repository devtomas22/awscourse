Summary

  • What telemetry monitoring is — an automated process for collecting data from a remote source to a central location at predefined time increments; in AWS that central place is CloudWatch, which stores the incoming data as CloudWatch Metrics. The point of the collection: identify system performance, detect and resolve issues (troubleshooting insights into what is happening with your cloud resources), and optimize workloads. CloudWatch is the central repository for metrics information — services send metrics in, alarms are created from those metrics, and rules can even action other services.
  • Which services send metrics in (course taxonomy, not exhaustive) — compute: EC2, auto-scaling groups, ELB (Elastic Load Balancer), Route 53 health checks, Lambda; storage and content delivery: EBS volumes, Storage Gateway, CloudFront; database and analytics: DynamoDB tables, ElastiCache, RDS instances, Redshift, EMR (Elastic MapReduce); other: Simple Notification Service, Simple Queue Service, and Simple Workflow.
  • Metrics hierarchy — and namespace isolation — metrics are stored in a hierarchy: at the top is the namespace (course examples: billing, config, EC2, S3), stepping down to dimensions (e.g. the EC2 per-instance metrics), and within them the individual metrics collected per instance — examples per the course: Networking, CPU Credit Balance, CPUUtilization, EBS Read Bytes, EBS Write Bytes. Docs ground it: a namespace is a container for metrics, there is no default namespace (you specify one per data point), AWS namespaces use the AWS/service convention (AWS/EC2), and metrics in different namespaces are kept separate so applications never blend into the same statistics. Dimensions then scope the hunt — the demo filtered Per-Instance Metrics by the instance’s Instance ID to land on exactly one CPUUtilization.
  • Basic vs detailed monitoring — and their consequences — Basic: automatically enabled by default on resources, free, metrics collected every five minutes — so an alarm on basic data evaluates five-minute data points. Detailed: only certain resource types, charged, every one minute — used when the application needs the extra monitoring level (production workloads, troubleshooting). Per today’s docs, EC2 detailed publishes at one-minute intervals instead of the five-minute basic intervals, and the level has different names per service (EC2: detailed monitoring; Elastic Beanstalk: enhanced monitoring; S3: request metrics).
  • Where metrics live and die — metrics exist only in the Region where they are created (a missing dashboard starts with a Region check); they cannot be deleted but automatically expire after 15 months if no new data is published.
  • CloudWatch agent — a downloadable package supported across a wide variety of operating systems (today’s docs list Amazon Linux 2023/2, Ubuntu, RHEL, Debian, SLES, Oracle, Alma, Rocky, macOS, Windows Server and desktop Windows), used when you need custom metrics gathered for applications on EC2 instances, containers, or on-premises servers. Memory and page file usage sit inside the OS, outside default collection — the in-guest system-level metrics the standard set misses are its headline fills, plus pulling configured logs into CloudWatch Logs. A wizard helps configure the collection; install the agent manually through the CLI, or through AWS Systems Manager — configure it once and reuse that configuration file on other EC2 instances (and on-premises servers too).
  • CloudWatch Logs — structure, then economics — centralize your log files from cloud resources, then apply log searches for insights. Log events form a Log Stream; streams gather into a Log Group. Two log classes: Standard (full-featured: log anomaly detection, Live Tail to see the end of the log file update near real time, API operations like get-log-events and filter-log-events) and Infrequent Access — renamed Essentials in today’s docs (docs note it applies from December 2026 to API responses) — a basic, feature-subset class that is cheaper and good for log files you don’t query often. The classes differ only in ingestion costs; a log group’s class can’t be changed after creation.
  • Log types and ways to send — Vended logs: logs you enable through different AWS services, predefined for that service (e.g. CloudTrail API activity, RDS database logs), though you may still configure delivery into CloudWatch Logs. Custom logs: managed and configured by you — e.g. the CloudWatch agent on an EC2 instance gathering system or application-level logs. Three custom ways to send: the CloudWatch agent, the AWS CLI PutLogEvents command, and the PutLogEvents API (programmatic bulk upload). Metric filters translate log data into a numerical CloudWatch Metric that can itself be actioned — logs turned into numbers that can then be alarmed.
  • Alarms are a state machine — three states: In alarm (the metric hit the configured value), OK (within threshold, nothing to investigate — the ones we like), Insufficient data (not enough data collected yet to tell). A brand-new alarm shows Insufficient data until enough five-minute data points have arrived — the demo watched exactly this timeline: insufficient data → in alarm.
  • The notification path is prebuilt — push notifications go to registered endpoints so nobody has to stare at the metric dashboard. They’re sent through Simple Notification Service, already integrated into CloudWatch — no code needed: create a topic, register an endpoint (e.g. an email address), confirm the subscription, and configure the alarm to use the topic; when the threshold is reached, the email arrives.
  • The demo, start to finish — EC2 instance cloudwatchalarmtest (Amazon Linux, t3.micro, no key pair) → SNS console: create a Standard topic cloudwatchalarmtopic + Email subscription (confirmed from the inbox) → EC2 Instance Connect: sudo dnf install stress -y → EC2 Monitoring tab shows the default metrics → CloudWatch console → Metrics → All metrics → EC2 namespace → Per-Instance Metrics → filter by the Instance ID → select CPUUtilization (graph: started at 23.92, down to 0.253 over one hour) → Create alarm (button or the chart’s bell icon; metric pre-populated), period five minutes, threshold CPUUtilization > 10%, notify via the existing SNS topic, name ec2cpuutiliz → alarm initially insufficient data (collecting data points) → sudo stress --cpu 1 loads the CPU → CPUUtilization climbs to 18.395 → alarm In alarm (visible under Alarms → In alarm filter) → the SNS email arrives: threshold crossed, one out of the last one data point greater than the threshold of 10.

Main concepts

Telemetry monitoring & CloudWatch in one card
Telemetry monitoring = automated collection of data from a remote source into a central location, at predefined time increments. In AWS that location is CloudWatch: it collects the data (mainly as metrics), helps identify system performance, detect/resolve issues with troubleshooting insights, and optimize workloads — and it acts as the central repository for metrics, from which you create alarms and rules that action other services.
Where CloudWatch metrics come from
Four course categories of senders: compute (EC2, auto-scaling groups, ELB, Route 53 health checks, Lambda), storage & content delivery (EBS volumes, Storage Gateway, CloudFront), database & analytics (DynamoDB tables, ElastiCache, RDS instances, Redshift, EMR), and other (SNS, SQS, Simple Workflow). Not an exhaustive list — but it puts every family on the map.
The metrics hierarchy: namespaces, dimensions, metrics
Metrics are stored in a hierarchy. Top level: namespace (billing, config, EC2, S3...). Next level: dimensions — under the EC2 namespace lives the per-instance metrics dimension. Inside a dimension are the actual metrics for each instance (Networking, CPU Credit Balance, CPUUtilization, EBS Read Bytes, EBS Write Bytes). Docs: a namespace is a container for metrics — metrics in different namespaces stay isolated so applications don’t get mixed into the same statistics; no default namespace exists, and AWS namespaces follow the AWS/service convention (AWS/EC2).
Basic monitoring
Automatically enabled by default on resources, free, and collects metrics every five minutes. This is what the EC2 Monitoring tab shows out of the box, and what the demo plotted for CPUUtilization.
Detailed monitoring
Only enabled for certain resource types; it is charged; and it collects metrics every one minute. Use it when the application requires the additional monitoring level — e.g. production workloads — or for troubleshooting. Docs nuance: for EC2, detailed publishes one-minute intervals vs the five-minute basic intervals; and the same idea carries different names across services (EC2 = detailed, Beanstalk = enhanced monitoring, S3 = request metrics).
Two docs facts worth knowing
Metrics exist only in the Region in which they are created — a regional fact to remember when hunting for a metric. And metrics cannot be deleted: they automatically expire after 15 months if no new data is published (on a rolling basis).
CloudWatch agent
A downloadable package for custom metrics when defaults aren’t enough — for applications running on EC2 instances, containers, or on-premises servers. Supported across a wide variety of operating systems (Amazon Linux 2023/2, Ubuntu, RHEL, SLES, Oracle/Alma/Rocky, macOS, Windows Server and client). It collects internal system-level (in-guest) metrics that the standard set lacks — like memory and page file usage — plus logs you configure to pull into CloudWatch Logs. You configure it with a wizard.
Installing the agent: CLI or Systems Manager
Two supported paths: install manually through the CLI, or through AWS Systems Manager — configure the agent once, then reuse that configuration file to install it on other EC2 instances in the environment. It also installs onto internal (on-premises) servers, so their metrics and log information reach CloudWatch.
What CloudWatch Logs is
A service to centralize log files from your cloud resources into one central location; from there you apply log searches for insights into what’s going on. The agent sends log information into it, and logs can be investigated with queries.
The two log classes
Standard: full-feature rich — log anomaly detection, Live Tail (watch the end of the log file update near real time), and API operations like get-log-events and filter-log-events. Infrequent Access: a basic feature set at a lower cost — good for log files you don’t query often. Today’s docs add: the Infrequent Access class is being renamed Essentials (formerly Infrequent Access); a log group’s class can’t be changed after creation; the two classes differ only in ingestion costs (same storage and insights charges).
Metric filters
You can filter the log data being received with metric filters, which translate logs into a numerical CloudWatch Metric — and that metric can then itself be actioned (e.g. alarmed on). A neat bridge between the Logs world and the Metrics world.
Vended logs vs custom logs
Vended logs: logs enabled through different AWS services, predefined specifically for that service — e.g. CloudTrail API activity or RDS database logs; no custom configuration needed for the log type itself, though you may still configure delivery into CloudWatch Logs. Custom logs: managed and configured by you — application and system-level logging from configured resources (e.g. install the agent on EC2 and point it at your system/application logs).
Log events, streams, groups — and three ways to send
The log events that get sent are a Log Stream, gathered into a Log Group. Three custom ways to send log information into CloudWatch Logs: the CloudWatch agent, the AWS CLI using the PutLogEvents command, or the PutLogEvents API for programmatic bulk upload.
The three alarm states
In alarm: the metric hit the value you configured — something to act on. OK: not within the threshold; nothing needing investigation (these are the ones we like). Insufficient data: not enough data collected in that present moment to determine whether the metric is okay or has breached the threshold — exactly what the fresh demo alarm showed while it collected data points.
From alarm to inbox with SNS
Push notifications to registered endpoints remove the need to watch the metric dashboard. They’re sent through Simple Notification Service — already integrated into CloudWatch, so no code: create the SNS topic, register an endpoint with it (an email address), confirm the subscription from the inbox, then configure the CloudWatch alarm to use the topic. When the threshold is reached, the email arrives describing which data point crossed which threshold.
The first-alarm demo, step by step
1) Launch EC2 cloudwatchalarmtest — Amazon Linux, t3.micro, no key pair. 2) SNS: create a Standard topic cloudwatchalarmtopic, add an Email subscription, confirm from the mailbox. 3) EC2 Instance Connect: sudo dnf install stress -y. 4) EC2 Monitoring tab shows the default metrics. 5) CloudWatch → Metrics → All metrics → EC2 namespace → Per-Instance Metrics → filter by Instance ID → select CPUUtilization (23.92 falling to 0.253 over an hour). 6) Create alarm (button or bell icon on the chart; metric pre-populated): period 5 minutes, threshold greater than 10%, notify via the existing SNS topic, name ec2cpuutiliz. 7) It starts insufficient data; run sudo stress --cpu 1; refresh over a few minutes; CPU hits 18.395 → alarm shows under Alarms → In alarm, and the email lands: 1 out of the last 1 data point greater than the threshold of 10.

Show answer

5. The three alarm states — and which one does a brand-new alarm show?

Show answer

6. Standard vs Infrequent Access (Essentials) log classes — and what today’s docs changed.

Show answer
Standard: full-featured (anomaly detection, Live Tail, get-log-events/filter-log-events). Infrequent Access: basic features, cheaper, for rarely-queried logs. Docs today: renamed Essentials (formerly Infrequent Access); the class can’t be changed after creation; classes differ only in ingestion costs.

1. Your production EC2 app needs per-minute visibility on its existing metrics — cost is accepted.

Show answer
Turn on detailed monitoring: one-minute intervals instead of the five-minute basic ones; charged and only for certain resource types (EC2 supports it — and remember Beanstalk calls it enhanced monitoring, S3 request metrics).

2. You need visibility into memory usage — but it isn’t in the default metric set.

Show answer

3. A year of archived access logs you nearly never query — keep costs down.

Show answer
The Infrequent Access log class — basic feature set, cheaper. Today’s docs: renamed Essentials, differing in ingestion costs only — and choose the class at creation, because it can’t be changed after.

4. The on-call engineer must get an email whenever CPU breaches 10% — without custom code.

Show answer

5. You must watch a log stream live while reproducing a fault, and turn recurring ERROR lines into a numeric metric later.

Show answer
Standard log class gives Live Tail (near real-time tail) — and a metric filter can translate those ERROR occurrences into a numerical CloudWatch Metric you can alarm on.

6. A teammate can’t find the metric for an instance “missing” all morning in the console.

Show answer
Check the Region — metrics exist only in the Region where they’re created (the vanished-resource trio from yesterday’s day page applies here too: account → region → permissions).
