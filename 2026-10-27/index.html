Summary

Today was the AWS Networking Fundamentals day — Amazon VPCs from first principles:

  • What a VPC is — your own logically isolated slice of the AWS network, scoped to a single region, with an IP range (CIDR) you define; nothing gets in or out until you configure it. Default VPCs exist for quick starts (always 172.31.0.0/16, auto public IPs) but are insecure; custom VPCs give you total control.
  • Three networking zones — the public internet (outside AWS), the public AWS zone (directly internet-connected: S3, DynamoDB, IAM, internet gateways) and the private AWS zone (your VPC resources, like EC2).
  • Drawing the network — subnets each bind to one availability zone and carry their own CIDR from the VPC block, public/private tiers give high availability by spreading across AZs; one route table per subnet (local route stays, public tables add the default route to the internet gateway); an internet gateway for real public reach, a NAT gateway for outbound-only private access.
  • Security controls — security groups: instance/network-interface level, stateful, allow-rules-only with implicit deny; network ACLs: subnet level, stateless, both allow and deny rules, allowing everything by default — return traffic usually needs the ephemeral range 1024-65535.
  • Addressing and DNS details — five IPs reserved in every subnet CIDR (CIDR+1 the VPC router, CIDR+2 the Route 53 Resolver); exactly one, immutable DHCP option set per VPC controls DNS servers, domain name, NTP and resolution.
  • Troubleshooting and beyond — the inside-out checklist (security group → NACL → route table) and VPC Reachability Analyzer for hop-by-hop paths; at scale: VPC peering (exactly two), Transit Gateway (central hub), site-to-site VPN (IPsec) — all reusing the same fundamentals, and a simple one-VPC design is often enough.

Main concepts

Amazon VPC
Your own logically isolated slice of the AWS network. Scoped to a single region (never global) with an IP range — the CIDR — that you define; nothing gets in or out until you configure it. Inside, you control network isolation, subnet blocks, routing, IP addressing and even custom DNS, and can deploy across multiple availability zones.
Default vs custom VPC
Every account ships with one default VPC per active region: instances just work, but it auto-assigns publicly accessible IPs and holds a default route to the internet gateway — highly insecure, meant for initial testing only, and always the 172.31.0.0/16 CIDR. A custom VPC is the opposite: you design every piece — isolation, subnet blocks, routing, addressing, DNS.
The three networking zones
Keep three zones straight: the public internet zone (everything publicly reachable outside the AWS network), the public AWS zone (a portion of AWS’s own network directly connected to the internet — S3, DynamoDB, IAM, internet gateways), and the private AWS zone (isolated from both — the resources you deploy inside your VPC, like EC2). Public reach is always something you design explicitly.
Subnets, tiers and AZ binding
A subnet is a resource in your VPC holding a range of IPs assigned from the VPC CIDR; resources like EC2 deploy inside subnets. Each subnet binds to exactly one availability zone — high availability means spreading subnets across several AZs. A two-tier design groups public (internet-facing) and private (internal) subnets into separate tiers.
Route tables — directions, not delivery
Every subnet gets one route table assignment. Route tables decide where traffic is allowed to go by target IP — they provide directions but never send traffic. Every table carries the local route (all VPC-CIDR traffic stays internal — subnets reach each other with no extra routes); public tables add the default route (0.0.0.0/0 toward the internet gateway). A new VPC ships with a main route table that any subnet lacking an explicit assignment falls back to.
Internet gateway
The resource that brokers internet traffic for the VPC — create it, then attach it to the VPC (it does nothing while unattached). Two things must hold for a resource to use it: a route pointing at the gateway, and a publicly resolvable IP. “Public subnet” is just a name until both are true.
NAT gateway
For private instances that must reach the internet securely without being reachable themselves: outbound connections work, but external traffic cannot initiate connections inbound. It must deploy into a public subnet with a public route and IP — that is how it reaches the internet at all.
Security groups
A stateful virtual firewall attached to an instance or network interface. Allow rules only — everything else is implicitly denied — and stateful: once inbound traffic is allowed, the response traffic is automatically allowed back out. Multiple security groups can attach to one interface and combine into one logical rule list.
Network ACLs
The subnet-level traffic filter. Separate inbound and outbound rule sets, allow AND deny rules, and stateless behavior: return traffic needs its own explicit rule. A network ACL created with your VPC allows all traffic in both directions by default (single rule 100).
Layered defense
Depth in layers: the NACL filters at the subnet boundary, the security group protects the instance and its network interface, and an optional host-based firewall adds a third layer — at least three controls in front of a resource.
Reserved IPs and the Route 53 Resolver
AWS reserves five addresses in every subnet CIDR — a /27 with 32 addresses yields only 27 usable. Two matter here: CIDR+1 is the VPC router (10.0.0.1 in 10.0.0.0/27) and CIDR+2 is the Route 53 Resolver — the VPC’s built-in DNS (10.0.0.2).
DHCP option sets
The group of network settings your VPC resources use: default or custom DNS servers, a custom domain name, custom NTP servers, and DNS resolution on/off. Exactly one option set is assigned to a VPC — and once created it can never be modified: create a new one, assign it, delete the old.
Assembling the two-tier demo VPC
Region first (VPCs are regional — the demo used us-east-1). Create the VPC with VPC only, name it, assign 10.0.0.0/24 (an RFC 1918 private range). Three things ship with a new VPC: a default NACL (allow-all), the main route table, and the default DHCP option set (domain AmazonProvidedDNS). Add four /27 subnets — public-a, public-b, private-a, private-b across two AZs (32 IPs each, 27 usable).
Wiring routes, gateway and security groups
Create one route table per subnet (the stated best practice) and associate each. Attach an internet gateway; on the public tables add the default route → IGW. Enable auto-assign public IP on the public subnets. One security group per tier: the public one allowing ICMP, SSH and HTTP from anywhere (sandbox-only — restrict it in real life), the private one allowing ICMP from the VPC CIDR — or better, from a security-group reference.
Proving connectivity
SSH to the public instance by public IP with the key pair (chmod the key first; the default username shows in the console’s Connect panel), then ping the internet. SSH into the private instance is impossible — no public IP, no resolvable address — but from the public instance you can ping it across the local route, the typical multi-tier pattern. A “private” instance with a manually enabled public IP still fails: without an IGW route, nothing reaches it.
The troubleshooting checklist
Inside-out, every time: 1) security group — are the allow rules right at the instance/network interface; 2) NACL — inbound AND outbound at the subnet (the stateless trap); 3) route table — does the traffic have a path. The three break-fixes: a missing default route to the IGW on one public subnet; outbound rules missing the ephemeral range 1024-65535 (response traffic never comes from the connecting port); and a private group sourcing a CIDR no subnet uses — best fixed by referencing the public security group instead of a static IP block.
VPC Reachability Analyzer
Create an analysis path — a source (e.g. the internet gateway), a destination (an instance), a destination port (TCP 80; the source side is ephemeral) — and the analyzer reports every hop: internet gateway → network ACL → network interface, with the failing component and its reason (“security group rules are mismatched”). Fix, re-analyze, confirm every hop green.
Advanced patterns — and when simple is enough
Three shapes scale past one VPC, all reusing the same fundamentals: VPC peering (a direct connection between exactly two VPCs), Transit Gateway (a central hub connecting several VPCs), and site-to-site VPN (an encrypted IPsec tunnel from on-premises into your VPCs). The counterpoint: single account, single region, no VPN needs and no compliance inspection means a simple one-VPC design is usually enough — just plan ahead for growth.

VPC endpoints
Private paths from your VPC into AWS services — no public internet, no NAT. Gateway endpoints (S3, DynamoDB): free, appear as a route-table entry. Interface endpoints (PrivateLink): elastic network interfaces with private DNS in your subnets, billed hourly per AZ plus a per-GB data processing fee (from $0.01/GB) — they also cut the data-transfer cost story short when an S3 fetch would otherwise cross the NAT gateway.
PrivateLink — publishing your own service
The other direction of the same trick: an endpoint service exposes YOUR application privately to other VPCs or accounts — consumers get an interface endpoint and a private DNS name, no VPN, no peering, no public IP anywhere. This is how SaaS-on-AWS keeps traffic inside the AWS network.
The two DNS switches
enableDnsSupport powers the VPC's Route 53 Resolver; enableDnsHostnames gives instances with public IPs public DNS names (private hostnames come automatically). Both default true. Flip either off and private-name resolution — think RDS endpoints or instance-to-instance calls — starts failing in ways that look like routing problems.
VPC Flow Logs
Traffic metadata (accept/reject, source/destination, ports, bytes) captured at VPC, subnet or ENI level and shipped to CloudWatch Logs or S3. The objective witness for troubleshooting the security-checklist items — did the packet even reach and get accepted? — and for auditing who talked to whom.
Security-group rule sources
Rules can reference another security group as the source instead of a CIDR — every member of that group is allowed and membership changes apply instantly (fleet patterns). The default security group carries a self-referencing rule that lets its own members talk freely. Stateful connection tracking means replies flow back without an outbound rule.

Quizzes

1. In one sentence, what is an Amazon VPC?

Show answer
Your own logically isolated slice of the AWS network, scoped to a single region, where you define the IP range (CIDR) — nothing gets in or out until you configure it.

2. Name the three networking zones with one example resource each.

Show answer
Public internet — everything outside the AWS network. Public AWS zone — directly internet-connected: S3, DynamoDB, IAM, internet gateways. Private AWS zone — resources deployed in your VPC, like EC2.

3. Default vs custom VPC — give two concrete differences.

Show answer
Default: one per active region, always 172.31.0.0/16, auto-assigns public IPs with a default IGW route, insecure — testing only. Custom: you design everything (CIDR, subnets, routes, DNS).

4. List the pieces you build for the two-tier demo VPC.

Show answer
The VPC (10.0.0.0/24), four /27 subnets (two public, two private) across two AZs, one route table per subnet, an attached internet gateway, one security group per tier, and two instances to test with.

5. Security group vs network ACL — level, rule kinds, statefulness, defaults.

Show answer
SG: instance/ENI level, allow-only, stateful, allows nothing by default. NACL: subnet level, allow and deny rules, stateless, allows everything by default.

6. An instance has a public IP but nothing can reach it. The route table holds only the local route. What is missing?

Show answer
The default route (0.0.0.0/0 → internet gateway) on that subnet’s route table — a public IP alone is unreachable.

7. How many IPs does AWS reserve per subnet CIDR, and which two does this course single out?

Show answer
Five. CIDR+1 is the VPC router (10.0.0.1), CIDR+2 is the Route 53 Resolver (10.0.0.2) — in a 10.0.0.0/27 that leaves 27 usable.

8. What can a DHCP option set configure, and what happens if you set one up wrong?

Show answer
DNS servers, the domain name, NTP servers, DNS resolution on/off. It is immutable after creation — create a new set, assign it, delete the old one.

9. State the troubleshooting checklist and why it starts where it starts.

Show answer
Inside-out: security group → NACL → route table — starting with the control closest to the resource (the instance/network interface), a repeatable order every time.

10. Which tool maps a network path hop-by-hop, and what did the failing network interface report?

Show answer
VPC Reachability Analyzer; the ENI hop failed with “security group rules are mismatched”.

1. Customers cannot reach one web server; its security group and subnet NACL both look correct.

Show answer
Check the route table (checklist step three): it held only the local route — add the default route 0.0.0.0/0 → internet gateway.

2. Two web servers go down together. Inbound 80 is allowed; outbound allows only port 80.

Show answer
The NACL is missing the ephemeral range — allow outbound TCP 1024-65535; response traffic never comes from the connecting port.

3. Public instances cannot ping the private back-end. The private group’s source CIDR matches no subnet in the VPC.

Show answer
Replace the static CIDR with a security-group reference (the public group) — membership-based, no IP bookkeeping.

4. SSH from your laptop fails on a fresh instance with a public IP in a public subnet. Where do you start?

Show answer
Checklist step one: the security group — is SSH allowed from your source? Then confirm the route table points the default route at the IGW.

5. Private instances need internet access for updates but must stay unreachable from outside.

Show answer
A NAT gateway in a public subnet — private instances initiate outbound; external traffic cannot initiate inbound.

6. You must debug traffic between the tiers hop-by-hop without walking the console.

Show answer
VPC Reachability Analyzer — create a path (internet gateway → instance, TCP 80) and read the per-hop results with the failing component’s reason.

7. Two VPCs owned by two teams need to talk — nothing more.

Show answer
VPC peering — a direct connection between exactly two VPCs, still steered by route tables, security groups and NACLs.

8. A corporate office needs a private, encrypted path into the VPC.

Show answer
A site-to-site VPN — an encrypted IPsec tunnel from the on-premises network into the VPC.

9. Five-plus VPCs across accounts need one central connection point.

Show answer
Transit Gateway — the central hub connecting several VPCs; the same fundamentals still steer traffic.

10. Single account, single region, no VPN needs, no compliance inspection — is peering or TGW required?

Show answer
No — this is exactly the profile where a simple one-VPC design is enough; just plan ahead in case requirements grow.
