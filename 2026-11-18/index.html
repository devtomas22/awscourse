Summary

  • Selecting a pre-trained foundation model is a checklist, not a vibe. Cost, modality (text → Bedrock models like Claude for chat, summarization, translation; image → Rekognition for objects, faces, moderation; audio → Transcribe speech-to-text, Polly text-to-speech), latency (low for real-time chat, relaxable for batch), multilingual support, model size (bigger often answers better but costs more to run), complexity to the task, customization options, and input/output length — the official task list adds prompt caching.
  • Inference parameters tune generation during the inference phase (the stage a trained model applies learned knowledge to new input). Temperature sets the randomness/creativity dial — low ~0.2 gives deterministic coding-friendly output, high ~0.8 suits story or marketing copy. Top-k samples by count of candidates; top-p samples by percentage of the probability mass; both read the same way: lower = smaller pool = safer outputs. Input/output lengths set what the model can take in and produce — short is less, long is more, and longer always costs more. AWS docs note the valid ranges are model-dependent (Claude: temperature 0–1.0, top-k up to 500).
  • RAG pairs a model with an external knowledge base — a structured repository of documents, FAQs, or research the model retrieves from at inference, then augments its prompt and generates from — giving up-to-date, context-aware answers without retraining. Amazon Bedrock Knowledge Bases can build one from S3-uploaded data; the vector stores holding the embeddings are OpenSearch Service (semantic and keyword search), Aurora PostgreSQL, RDS for PostgreSQL with pgvector, Neptune (graph relationships), DocumentDB (schemaless) — and S3 Vectors (GA Dec 2025) stores embeddings natively in S3.
  • Customization is a cost ladder. Pre-training from scratch = very high cost, full control (provider-scale). Fine-tuning with task-specific labeled data = moderate. In-context learning (prompts only) = lowest, only inference. RAG = lower than fine-tuning, external data, easy updates. Docs update: Bedrock custom models can now deploy on-demand for inference; Provisioned Throughput remains the guaranteed-capacity route.
  • Agents for Amazon Bedrock automate multi-step workflows: retrieve from company sources (RAG), call APIs across systems, dynamically generate code, with memory retention for personalization and action schemas for async tasks — e.g., an order-status agent that reads the database, analyzes shipping state, and answers in real time.
  • Prompt engineering = giving the model a recipe. Constructs: context frames the task (“to a beginner”), clear instructions set output expectations, negative prompts exclude what you don’t want, and the model’s latent space — its internal map of clustered, related concepts — is what your prompt navigates. Techniques: zero-shot (no examples → broad) → single-shot → few-shot (examples steer focus) → chain-of-thought (step-by-step reasoning → accuracy on complex tasks) → prompt templates (standardized placeholders translate user input into instructions).
  • Practice and risk are two sides. Practices: be specific and concise, experiment to discover what the model can do, use guardrails (explicit exclusions) to cut bias and keep answers relevant, and prefer multiple follow-up prompts over one giant one. Risks: exposure (sensitive data leaks through prompts/prompt content), poisoning (false data inserted during training), hijacking (attacker redirects the model’s behavior), jailbreaking (clever prompts bypass safety constraints) — each has its mitigation, from filtering training data to enforcing usage policy.
  • Training/evaluation closes the loop. Pre-training → fine-tuning (methods: instruction tuning, domain adaptation, transfer learning, continuous pre-training) → data preparation (curation, governance, representativeness over raw size, labeling, RLHF with a reward model). Evaluate with human evaluation (nuanced, subjective, slow) or benchmark datasets (objective, scalable, less bias, weaker on niche tasks), reading ROUGE (summarization recall), BLEU (translation), BERTScore (embedding similarity) for automated metrics — the exam guide also names LLM-as-a-judge and Bedrock Model Evaluation. Business alignment = productivity, user engagement, and task effectiveness, the course terms it "task engineering". Exam: Domain 3 is 28% — the largest AIF-C01 domain.

Main concepts

Five clusters — model selection, inference control, RAG and vector storage, customization/training, prompt engineering, evaluation — plus the two 2026 docs updates.

Model selection criteria
The exam’s official list: cost, modality, latency, multi-lingual, model size, model complexity, customization, input/output length, prompt caching (task 3.1). Modality mapping on AWS: Bedrock models like Claude power chatbots, document summarization, translation; Rekognition does image recognition, face detection, moderation; Transcribe turns speech to text for call centers and Polly turns text into natural-sounding voices. Big models may answer more accurately but need extensive compute; small models deploy cheap. Match latency to the workload (real-time chat vs batch analysis) and multilingual capability to the audience.
Inference parameters in depth
Temperature (e.g., 0.2 vs 0.8) balances deterministic vs creative — for describing the Eiffel Tower, low returns a factual line, high returns a florid one. Top-k = the number of most-likely candidate tokens considered (the pool size); top-p = selecting from the top percentage of the probability distribution (0.9 = top 90%). In Bedrock both are tunable per model. Docs note (Nov 2026): ranges and defaults are model-dependent — the course’s 0–500 top-k figure is the Claude family’s maximum; longer inputs/outputs raise cost and compute.
RAG and knowledge bases
A knowledge base is a structured repository — company docs, FAQs, research papers — the model is allowed to reference at inference. Bedrock Knowledge Bases builds one from data uploaded to S3. RAG flow: retrieve relevant items, augment the prompt with them, generate a grounded answer — used in customer support (current FAQs), engineering documentation (exact spec lookups), research analysis (query databases). Cost appeal: no weight changes, updates to the KB take effect without retraining.
Vector storage on AWS
Embeddings convert inputs into numeric vectors capturing semantic meaning; vector databases index and query them by similarity rather than exact match. Services: OpenSearch Service (vectors + full-text keyword search — the semantic-plus-keyword pick), Aurora PostgreSQL (relational + vectors for personalized recommendations), RDS for PostgreSQL (pgvector extension), Neptune (graph relationships between embeddings), DocumentDB (schemaless, document data alongside), and S3 Vectors — GA December 2025, native embedding storage in S3 buckets with up to 90% cost reduction and Bedrock Knowledge Bases integration.
Customization cost ladder
Pre-training: building a model from scratch — very high compute plus storage, only for big organizations or domains with no usable base model (a bank pre-training for proprietary fraud detection). Fine-tuning: updating a pre-trained model with a smaller task-specific dataset — moderate cost (financial institution fine-tuning for patient-record analysis). In-context learning: guide output through prompts only — pay for inference, that’s it. RAG: pre-trained model + external data — cheaper than fine-tuning, perfect for real-time updating needs (retail inventory chatbot).
Docs update: serving custom models
The course says: to invoke a customized model in Bedrock you must purchase Provisioned Throughput — guaranteed, predictable capacity billed hourly, and still the classic path. Current Bedrock docs (checked Nov 2026) add a second option: deploy a custom model for on-demand inference — pay only for what you use with no provisioned compute. Exam framing: know Provisioned Throughput as the dedicated-capacity answer; know on-demand as the newer pay-per-use route.
Training and fine-tuning methods
Pre-training = learn general capability from vast unstructured data; fine-tuning = customize with task-specific data; continuous pre-training = keep learning new info while retaining the old (fresh support tickets without forgetting how to answer). Fine-tuning methods: instruction tuning (train on prompt/response examples to follow directives — e.g., an empathetic tone), domain adaptation (further training on one industry’s data — legal, medical), transfer learning (a pre-trained model re-uses its knowledge for a new related task cheaply).
Preparing data to fine-tune
Curation: select and organize relevant, accurate, high-quality data, removing noise and redundancy (filter fiction out of a legal corpus). Governance: policies and processes ensuring quality, accuracy, privacy, and ethical use. Size matters — but quality and representativeness matter more; unrepresentative data bakes bias in. Labeling: annotate examples (spam / not spam). RLHF: human evaluators score responses; a reward model learns to predict response quality so the model aligns to human preference.
Agents for Amazon Bedrock
Bedrock agents extend foundation models into multi-step automation: follow predefined instructions, retrieve from company sources via RAG, dynamically generate code for complex queries, orchestrate API calls across systems, retain memory across a session, and expose action schemas for async tasks. Example: an order-status agent reads the order database, analyzes shipping state, responds in real time — no manual steps. Great for repetitive, data-driven workflows.
Prompt constructs
Context frames the task and narrows the response (“explain cloud computing to a beginner”). Instructions set format, tone, and content expectations precisely (“place the red folder on the top shelf”, not “somewhere easy to find”). Negative prompts name what to exclude (“without technical terminology”). The latent space is the model’s internal representation — clusters of related ideas (solar, wind, hydrogen → renewables; carbon footprint even when unrequested) used to connect concepts and generate outputs.
Prompt techniques and practices
Progression: zero-shot (no examples — relies on general knowledge, broad), single-shot (one example steers focus), few-shot (several examples set the expected shape), chain-of-thought (“break down your explanation into steps” — strong for math/complex problems), prompt templates (standardized placeholders — “Describe a [animal] including [traits]” — translate user input into consistent instructions; customer-support-friendly). Practices: specific and concise prompts, experimentation leading to discovery, guardrails to cut bias and unwanted content, multiple follow-up prompts instead of one monster prompt.
Prompt risks and their mitigations
Exposure — sensitive data leaks through prompts (asking for confidential project details the model was trained on; also your own sensitive data pasted in). Mitigate: avoid prompts targeting/containing sensitive or proprietary information. Poisoning — malicious false data in training corpora producing biased/dangerous outputs. Mitigate: filter training data, continuously evaluate outputs, detect and block harmful data. Hijacking — attacker manipulates a prompt to divert behavior. Mitigate: clear usage policies, prompt monitoring. Jailbreaking — clever prompts bypass safety constraints. Mitigate: robust guardrails, continuous vulnerability testing.
Evaluation methods and metrics
Human evaluation gives nuanced, subjective judgements but is time-consuming and inconsistent at scale; benchmark datasets are pre-built labeled collections scored objectively (accuracy, bias, fairness) with less admin effort, at the cost of niche-task specificity. Metrics: ROUGE (Recall-Oriented Understudy for Gisting Evaluation — n-gram overlap vs references; summarization recall), BLEU (Bilingual Evaluation Understudy — word-sequence matching for machine translation, 0 to 1), BERTScore (embedding-based semantic similarity — paraphrases with different words score high). The official task list adds LLM-as-a-judge and Bedrock Model Evaluation.
Business objective alignment
Productivity: how efficiently the model produces quality output with minimal human intervention. User engagement: how often and how deeply users interact — including how actively they refine prompts and responses (feedback is a good signal). Task effectiveness/“task engineering” (the course’s and the exam guide’s term): how smoothly and accurately the model completes business-aligned tasks. The task list also names application-level metrics: task completion rate, user satisfaction, cost per interaction — and evaluating complete applications (RAG, agents, workflows), not just raw models.

Flashcards

Modality
The type of data a model handles — text, image, or audio. Text: Bedrock (Claude etc.) for chat, summarization, translation; image: Rekognition; audio: Transcribe/Polly.
Latency (model selection)
How quickly a model processes requests — low latency for real-time chat, less critical for batch analysis.
Model size trade-off
Large models may perform more accurately but need extensive compute; smaller models are more efficient and easier to deploy.
Model complexity
How sophisticated the tasks a model can handle are — light models for simple tasks, robust multi-layer models for complex ones.
Multilingual support
Models pre-trained to support multiple languages serve a global audience without extra training.
Input/output length
How much text the model can take in and generate — short is less, long is more; longer always raises cost and compute.
Temperature
Inference parameter setting randomness vs determinism: ~0.2 = predictable (coding), ~0.8 = creative (stories, marketing).
Top-k
Sampling by count — the model considers only the k most likely candidate tokens (Claude: up to 500); lower k = smaller pool, more-likely outputs.
Top-p
Sampling by percentage — considers tokens covering p% of the probability distribution (0.9 = top 90%); lower p = safer outputs.
RAG
Retrieval-augmented generation: pair the model with an external knowledge source it queries at inference, augment the prompt, generate grounded answers — up to date, context-aware, no retraining.
Knowledge base
A structured repository (documents, FAQs, research papers) the model references at inference to improve accuracy; Bedrock Knowledge Bases can build one from S3 data.
Vector embeddings
Machine-readable numeric representations capturing semantic meaning — vectors are the arrays of embeddings.
OpenSearch for vectors
Amazon OpenSearch Service stores embeddings with full-text search — combined semantic and keyword retrieval (e.g., 'budget laptops' finds affordable listings).
Aurora PostgreSQL (vectors)
Extends the relational database to store vector data — used for personalized recommendations.
pgvector
The PostgreSQL extension that supports vector similarity search inside Amazon RDS for PostgreSQL.
Neptune (vectors)
The graph database — stores and queries relationships between embeddings for graph-based use cases.
DocumentDB (vectors)
Flexible, schemaless storage holding embeddings alongside document-based data.
S3 Vectors
GA Dec 2025: native vector storage inside S3 — cost-optimized embedding storage (up to 90% cheaper) integrated into Bedrock Knowledge Bases.
Pre-training
Building a model from scratch on vast unstructured data — very high cost, full control, provider-scale resources.
Fine-tuning
Updating a pre-trained model with a smaller task-specific dataset — moderate cost; requires prepared, labeled data.
Provisioned Throughput
Dedicated, guaranteed-capacity compute purchased to invoke a Bedrock custom model (billed hourly). Docs update: on-demand deployments of custom models are now also supported.
Continuous pre-training
Further training on new information while retaining what was already learned — keeps models current without forgetting.
Instruction tuning
Further training a model on input/response examples so it follows instructions better (e.g., tuning a chatbot to be more empathetic).
Domain adaptation
Further training a general-purpose model on data from one specific industry or field (legal, medical, finance).
Transfer learning
Fine-tuning a model pre-trained on one task for a new, related task — reuses learned knowledge, skipping from-scratch costs.
RLHF
Reinforcement learning from human feedback: evaluators score responses, and a reward model learns to predict response quality to align the model with human preferences.
Agents for Amazon Bedrock
Orchestrate multi-step workflows: retrieval from company sources (RAG), API calls across systems, generated code, memory retention, action schemas.
Prompt engineering
Crafting instructions and prompts that guide AI behavior — instructions to the model like a recipe guides a cook.
Context (prompt)
Background information that frames the task and narrows the response — 'explain cloud computing to a beginner'.
Negative prompt
Explicitly telling the model what not to include — 'without technical terminology'.
Latent space
The model's internal representation of knowledge — clusters of related concepts it uses to connect topics and generate outputs.
Zero-shot prompting
Giving a task with no examples — broad output, relying fully on the model's general knowledge.
Few-shot prompting
Providing multiple examples in the prompt to steer format and focus (single = one example).
Chain-of-thought prompting
Asking the model to break a complex problem into smaller logical steps — shows the reasoning process, improves accuracy (great for math).
Prompt template
A standardized scaffold with placeholders ('Describe a [animal] including [traits]') that translates user input into consistent model instructions.
Guardrails
Explicit constraints on prompts — 'don't include political opinions' — reducing bias and keeping outputs relevant and safe.
ROUGE
Recall-Oriented Understudy for Gisting Evaluation — measures overlap between generated and reference text (n-gram matching); the summarization/recall metric.
BLEU
Bilingual Evaluation Understudy — compares word sequences against references for machine-translation quality; scores 0 to 1.
BERTScore
Uses embeddings from pre-trained BERT models to compare semantic similarity between generated and reference text — paraphrases score high.
Benchmark datasets
Pre-built labeled collections scored against industry standards — objective, scalable, less bias, weaker on niche applications.

Answered 0 of 6 · First-try correct: 0

1. You are selecting a pre-trained foundation model for real-time language translation. Which pair of selection criteria leads the decision?

Real-time translation is led by latency, because responses must be produced fast, plus multilingual capability, because the model must actually translate. Size matters but is not the priority here.

2. Which metric fits machine translation by comparing word sequences, and which one measures semantic similarity through embeddings?

BLEU is the 0 to 1 word-sequence comparison used for translation, while BERTScore uses embeddings, so a paraphrase that changes the wording still scores high.

3. Which prompt-engineering technique breaks complex problems into sequential reasoning steps to improve response accuracy?

Chain-of-thought prompting breaks a complex problem into sequential reasoning steps and improves accuracy; templates standardize inputs, few-shot supplies examples, negative prompting only excludes content.

4. Which fine-tuning method customizes a model for one specific field such as legal or medical applications?

Domain adaptation further trains a general-purpose model on data from one industry or field such as legal or medical. Transfer learning targets new related tasks, instruction tuning targets instruction-following.

5. A company needs a scalable, objective method to evaluate text-generation models on semantic similarity and linguistic quality. What is the automated best pick?

BERTScore judges semantic meaning through embeddings, so it scales objectively. ROUGE and BLEU only compare overlapping word sequences, and human review is nuanced but subjective and slow.

6. A chatbot must answer from current company FAQs and manuals without any model retraining. Which technique-and-service pair?

RAG retrieves from a knowledge base built from your documents, augments the prompt and generates a current, context-aware answer with no retraining.

1. Marketing wants far more imaginative campaign copy and is fine with varied wording between runs.

A larger sampling pool trades determinism for variety, which is what imaginative copywriting needs; the low-temperature setting is the opposite lever.

2. A coding assistant must give dependable, repeatable suggestions.

A small candidate pool at low temperature yields the most likely, repeatable output, which is what a coding assistant needs.

3. Analysts query internal reports that change daily, and the team refuses to retrain a model weekly.

With RAG the reports live in the index and retrieval happens at inference, so daily updates are a re-sync rather than a retraining cycle.

4. A bank wants a fraud-detection model for a domain nothing off-the-shelf covers — and price is no object for the right answer.

Pre-training from scratch is the highest-cost route and is reserved for domains no off-the-shelf model covers; if a suitable base model existed, fine-tuning would be the moderate-cost answer.

5. A support lead wants the chatbot to respond more empathetically to complaints; they can supply sample prompts and desired responses.

Instruction tuning further trains on examples of inputs and desired responses, which is how you steer tone toward the style the lead described.

6. An e-commerce customer asks “what is the status of my order?”, and answering spans reading the order database, checking the shipper, and replying with live updates.

Agents orchestrate multi-step work: retrieval, API calls to the order and shipper systems, and a dynamic reply, with memory retention and action schemas and no manual step in between.
