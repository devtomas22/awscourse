Main concepts

Which workloads belong on EC2
A big class of workloads runs on EC2: web applications, inference jobs, tools that expect a full operating system underneath. An EC2 instance is a virtual machine running in AWS — you ask for compute and get it on demand, then scale one instance to hundreds when needed.
The four controls of an instance
1. CPU & memory customization · 2. OS control & server administration (choose, configure, administer like any server) · 3. Network addressing (public, private, or both) · 4. Storage management (kind and amount).
Rental-car analogy
The instance is the rental car — you didn't buy it or maintain the garage, but it's yours to drive while you pay. The instance type is the vehicle class: moped (small, cheap), delivery truck (heavy loads), race car (pure speed) — different combos of CPU, memory, networking, storage. An AMI is a snapshot of an operating system with pre-installed software.
Launch-time choices
Always tag (naming and tagging is optional but right). The summary panel lets you launch several identical instances at once. AMI from the Quick Start list — free-tier eligible resources are marked. Then instance type, key pair, security group, and an IAM role (needed later for Session Manager).
Connect: SSH (Linux)
EC2 console → Connect → SSH client gives you the command. The PEM file needs restricted permissions or ssh rejects it. Confirm the fingerprint, and you're in as ec2-user — the default user the EC2 service created — free to run commands on the server.
Connect: RDP (Windows)
Security group allows RDP only from your IP. Download the .rdp shortcut, then get the Windows password: upload the private key file, decrypt — the console reveals the admin username and password for the Remote Desktop login.
Connect: Session Manager (SSM)
A secure agent-based connection without any SSH or RDP. Two prerequisites, both required: network connectivity to the Session Manager service and IAM permissions on the instance role (the AmazonSSMManagedInstanceCore managed policy). You land as ssm-user — not ec2-user — but you can do all the same work from the browser shell.
Instance lifecycle & billing
Launch → pending (AWS finds hardware and boots the image; not billed) → running (billed, connectable). From running there are three moves: reboot (OS restart — same hardware, IP, and data; billing continues), stop (passes through stopping → stopped = shut down, not deleted), or terminate (end it).
Status checks & troubleshooting loop
Troubleshooting starts with diagnosis. Status checks read bottom-up: System status (AWS's side), Instance status (the OS reached its boot phases), EBS status (volumes reachable), Application status (your app-level checks) — a failing Application check with green System/Instance/EBS means the problem is your software, not AWS infrastructure. Fix for the failing layer, then watch the checks return green.
The compute spectrum
EC2 = buying groceries and cooking at home — total control, all the dishes. ECS = a meal prep kit — standardized ingredients, less prep, still cooking. Lambda = a restaurant — never see the kitchen, pay per plate, not per stove-hour. The pattern: moving from EC2 toward serverless trades operational burden for constraints — less to run, but less you may change.
Six strong EC2 cases
1. Full OS & kernel control (only EC2 offers it on the spectrum) · 2. Long-running, always-on workloads past serverless limits · 3. Specialized hardware (GPUs, chosen processors) · 4. Lift-and-shift migration (VM maps to a VM without rewrites) · 5. Predictable steady-state traffic (right-size for stable cost) · 6. Cost-optimized fault-tolerant batch (spot instances). When in doubt: start with EC2 — most flexible, refactor later if needed.

True / false — quick round

Pick your answer — it highlights green (correct) or red (wrong) and the explanation appears immediately.

You start being billed the moment your instance enters the pending state.

False — pending is not billed; billing starts in running.

Stopping an instance deletes it and its data.

False — stopped means shut down, not deleted; the data stays for when you power it back on.

A reboot keeps the instance on the same hardware with the same IP and data.

True — reboot is basically an OS restart; billing never skips a beat.

Session Manager works with no IAM permissions at all.

False — it needs both a network path to the SSM service AND permissions like AmazonSSMManagedInstanceCore on the instance role.

To get the Windows password over RDP, you upload your private key file and decrypt.

True — the console decrypts the admin password with the key pair you selected at launch.

The SSH key file needs restricted permissions before it will work.

True — without the permission change, ssh throws an error before you can connect.

You can launch several identical instances in one go from the same settings.

True — the count setting in the launch summary does exactly that, e.g. five identical servers.

Free-tier eligible resources are marked in the launch dialog.

True — look for the marking to stay within Free tier.

You log in as ec2-user when connecting through Session Manager.

False — Session Manager lands you as ssm-user; ec2-user is the SSH default user.

Lambda bills you per hour that the stove is running.

False — that's the EC2 model; Lambda is pay per plate: you pay per use, never seeing the kitchen.

ECS sits between EC2's full control and Lambda's full abstraction.

True — the meal-prep kit: standardized ingredients arrive, you still cook, but not from raw groceries.

Lift-and-shift works because a virtual machine maps naturally to an EC2 virtual machine.

True — moving existing servers without rewrites is one of EC2's strongest use cases.

Spot instances are a sensible pick for fault-tolerant batch workloads that flex with price.

True — flexible EC2 purchasing options trade price against fixed capacity.

When you can't open SSH or RDP ports, there is no way to reach an instance.

False — Session Manager connects without those protocols, given SSM permissions and network path.

Quizzes

1. In one sentence — what is an EC2 instance?

Show answer
A virtual machine running in AWS: you ask for compute, AWS gives it on demand — scaling from one instance to hundreds, with public, private, or both kinds of connectivity.

2. Server-based workloads map to four things EC2 puts in your hands — name them.

Show answer
CPU & memory customization · OS control & server administration · network addressing control · storage management.

3. In the rental-car analogy, what do the instance, the instance type, and the AMI each play?

Show answer
Instance = the rental car you drive while paying. Instance type = the vehicle class (moped / delivery truck / race car). AMI = the operating-system snapshot with pre-installed software the car boots from.

4. What is under the hood of your instance-type choice?

Show answer
Real choices: x86 or ARM processors, memory from very small to very large, standard vs advanced networking, and locally attached vs network-based storage.

5. Name the important choices the launch dialog walks you through.

Show answer
Name/tags, number of instances, AMI (Quick Start, free-tier markings), instance type, key pair, security group, IAM role.

6. The three ways to connect to an instance — and their target OS?

Show answer
SSH for Linux instances, RDP for Windows instances, and Session Manager for both — the agent-based browser shell that needs no SSH/RDP ports.

7. Session Manager has two prerequisites — what are they?

Show answer
A network connection to the Session Manager service AND IAM permissions on the instance (e.g. the AmazonSSMManagedInstanceCore managed policy). People forget one or the other.

8. What changes between connecting via SSH and via Session Manager?

Show answer
The user: SSH logs you in as ec2-user (created by the EC2 service), Session Manager lands you as ssm-user — same box, same work, different identity.

9. Walk the instance lifecycle from launch, and where billing starts.

Show answer
Launch → pending (hardware being found, image booting — not billed) → running (billed, connectable) → then reboot, stop, or terminate.

10. What's the core pattern of the compute spectrum?

Show answer
From EC2 toward serverless you trade operational burden for constraints — running a service gets easier, but what you may change shrinks. EC2 = cook at home; ECS = meal kit; Lambda = restaurant.

1. What exactly happens in the pending state?

Show answer
AWS is finding hardware and booting your instance from the chosen image — usually seconds, sometimes minutes. You are not billed during it.

2. Difference between stop and terminate?

Show answer
Stop passes through stopping into stopped = shut down, NOT deleted (power off, stored in your rack, data kept). Terminate ends the instance.

3. Why does a reboot not affect your billing?

Show answer
It's an OS restart: the instance stays on the same hardware, keeps its IP and data, and goes straight back to running — billing never pauses.

4. Which status checks make up the diagnosis picture?

Show answer
System status, Instance status, EBS status, and Application status — under Status and alarms on the instance.

5. System, Instance and EBS checks all pass, but Application status fails — where's the problem?

Show answer
At your application layer, not AWS infrastructure: the instance, its volumes, and AWS's side are healthy — investigate the software or app-level check.

6. What's the always-good troubleshooting loop?

Show answer
Diagnose before touching anything: read the symptoms via the instance states and status checks, identify the failing layer, fix it, then verify the checks pass again.

1. A web app plus an internal tool that expects a full operating system — where do they run?

Show answer
On EC2 — full OS control is exactly the class of workload it exists for, and it's the only spectrum option that gives OS/kernel control.

2. An always-on service would blow past serverless limits. What do you choose?

Show answer
EC2 — long-running, always-on workloads are a strong first move there, with predictable steady-state billing you can right-size.

3. Training needs GPUs and a specific processor. Serverless?

Show answer
EC2 — specialized hardware requirements (GPUs, chosen processor types) are a core EC2 strength.

4. Your company wants its existing VM fleet moved without rewriting anything. What's the path?

Show answer
Lift-and-shift onto EC2 — a VM maps naturally to a VM, no rearchitecture required.

5. Traffic is steady and predictable, and cost stability matters. What do you do?

Show answer
Right-size an EC2 instance for the steady-state load — capacity you control keeps costs stable.

6. A fault-tolerant batch job runs whenever capacity is cheapest. Which purchasing option?

Show answer
Spot instances — flexible purchasing for cost-optimized, fault-tolerant workloads.

7. Security forbids opening SSH or RDP ports. How do you reach your instances?

Show answer
Session Manager — attach the instance role with AmazonSSMManagedInstanceCore, ensure the SSM network path, and get a browser shell with zero inbound ports; log in as ssm-user.

8. ssh refuses your key with a permissions error. Fix?

Show answer
Restrict the PEM file's permissions (as the demo prepared before connecting) — then rerun the console-given SSH command, accept the fingerprint, and you're in.

9. Five identical web servers are needed immediately. What do you configure?

Show answer
The instance count in the launch dialog's summary — the same settings stamp out N identical instances in one go.

10. Boss asks: is EC2 "legacy" now that serverless exists?

Show answer
No — it's often the strongest first move: OS/kernel control, always-on loads, GPUs, lift-and-shift, steady traffic, spot batch. When in doubt, start with EC2 and refactor later.
