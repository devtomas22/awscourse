Day 2026-10-21 · IAM Fundamentals

Pluralsight: AWS Identity and Access Management Fundamentals (users & groups, roles & policies, monitoring) + own notes on policy anatomy.

Day 1Topic: IAMSource: Pluralsight + class notes

Summary

Spend-the-day deep dive on Identity and Access Management:

  • Authentication vs authorization — prove who you are (hotel check-in, passport) vs what you may do (the room card).
  • Account hierarchy — account (container, 12-digit ID, owns billing) → root user (permanent, all-powerful, NOT for daily work, strong password + MFA) → IAM users (friendly names, your password policy).
  • Users vs groups — groups are containers by job function: attach a policy once, all members inherit; can't nest groups; not a login identity.
  • Policies — identity-based (AWS-managed, customer-managed, inline) vs resource-based (has a Principal, enables cross-account); JSON syntax with Version 2012-10-17, Effect, Action, Resource, Condition; explicit Deny always wins.
  • Roles — assumable identities with temporary STS credentials and a trust policy. Identity roles give just-in-time access; service roles let AWS services (EC2, Lambda) act on your behalf without baked-in keys.
  • Monitoring — IAM credential report (CSV, all users' credential status, downloadable ~4 h) and CloudTrail (who did what, when, from which IP; ~90-day default history).

Main concepts

Account vs root vs user
Account: container created at signup (email address), 12-digit ID, owns resources + billing. Root user: the account's permanent all-powerful login — protect it (strong password + MFA), use only when necessary; AWS sets its password rules, and it cannot be removed. IAM user: friendly-named identity inside the account with its own password/keys and only what its attached policies allow. Console sign-in for an IAM user needs account ID + username.
Identity policy vs resource policy
Identity: attached to a principal (user/group/role), states what that identity can do — no Principal element. Resource: attached to a resource (S3 bucket policy, KMS key, SQS...), states who can access it — carries Principal. Only resource policies grant cross-account access directly. Both evaluate together; an explicit Deny in either wins.
Three identity-based policy forms
AWS-managed (AWS-curated, auto-updated for new services), customer-managed (specific, restricted, you own the maintenance), inline (single identity, not reusable elsewhere).
Identity role vs service role
Role: assumable identity — no long-term secrets; STS hands back temporary credentials; its trust policy defines who may assume it. Identity role: a user assumes it per-ticket for just-in-time permissions, then drops it. Service role: an AWS service assumes it (e.g. Lambda execution role, EC2 instance profile) — principal is the service like ec2.amazonaws.com or lambda.amazonaws.com, never a human.
User vs group vs roles (when to use which)
User: one long-term identity. Group: container for users — assign once, all inherit. Role for users: temporary STS elevation instead of permanent permissions (intern for a week). Role for service: only machines assume it.
Trusted entity types
AWS service (most common), AWS account (own or other accounts), Web identity (OIDC federation: Google/Facebook/Amazon/Cognito), SAML (corporate SSO), custom trust policy (hand-written Principal).
Monitoring IAM access
Credential report: generated CSV listing all IAM users — password age, MFA on/off, access-key status and last use; great for unused-key and no-MFA audits; storable ~4 hours after generation. CloudTrail: security camera for the account — every API call recorded (principal, account, event, time, source IP, device); ~90-day Event history by default, S3 delivery for long retention.
Policy syntax essentials
Version = policy language version ("2012-10-17", always) · Sid optional comment · Effect Allow/Deny, required, Deny wins · Action = service:operation, wildcards ok, NotAction = complement · Resource = ARN scope, NotResource = complement · Condition optional (e.g. aws:SourceIp) · Principal = resource-based policies only.

Flashcards

Click a card to flip it. Work through all 40 — terms from today's session.

ARN
Amazon Resource Name — the structured identifier for every AWS resource; it becomes second nature as you progress.
Root user
Permanent, cannot be removed, reaches everything in the account. Strong passphrase + MFA, locked away.
IAM group
Container for users, policies applied once and inherited by all members; can't nest; can't be used to log in.
Assume a role
Adopt a role you're trusted for: STS issues temporary credentials for as long as you need it, then release it.
Trust policy
Role sub-policy naming who may assume it — a service, an account, an OIDC/SAML provider... no trust, no assumption.
Service role
Role assumed by an AWS service acting on your behalf — Lambda execution role, EC2 instance profile.
Instance profile
EC2's wrapper for a service role: the instance fetches auto-rotating STS credentials — no access keys on disk.
Credential report
CSV snapshot of all IAM users' credential status; downloadable for up to 4 hours after generation.
CloudTrail
Security camera for the account: records every API call — who, what, when, source IP, device. ~90-day default history.
Explicit Deny
Beats any Allow anywhere in the policy evaluation order — safest way to fence something off.
Inline policy
Policy embedded in a single identity — not shareable or reusable elsewhere.
Web identity (OIDC)
Trusted-entity type for federated logins via Google / Facebook / Amazon / Cognito.
Authentication
Proving who you are — the hotel check-in: your passport establishes identity before a room card is issued.
Authorization
The room card: with identity proven, it decides what you may open — authentication comes first, authorization second.
AWS-managed policy
Curated by AWS for common use cases; when a new service launches, an AWS-managed policy can pick up access automatically.
Customer-managed policy
Your own policy for a very specific, restricted permission set — you own every change and every test.
Just-in-time access
Pick up a role for the ticket at hand, drop it after — extra permissions held only while the work lasts.
Account ID
The account's 12-digit identifier — an IAM user signs into the console with account ID + username together.
Security recommendations
The IAM dashboard's top banner — e.g. it tells you to add MFA on the root user when you sign in as root unprotected.
Trail in S3
CloudTrail's long-retention design: Event history keeps ~90 days, delivering logs to S3 keeps what you configure.
IAM user
A friendly-named account created in IAM for your daily work — it follows the password policy you set and holds only the permissions its policies grant.
Password policy
For IAM users, YOU set the password rules — the root user's is fixed by Amazon instead, so its strength is out of your hands except for MFA and usage discipline.
Identity policy
Attached to a principal (IAM user, group, or role) and states what that identity can do — it carries no Principal element.
Resource policy
Attached to a resource (S3 bucket, KMS key, SQS...) and states who may access it — it carries a Principal element.
Cross-account access
Resource policies are what enable cross-account access; identity policies alone only reach within the same account.
Principal
The who-may-access-this element — only in resource-based policies; identity policies don't have one.
Version
First element of every IAM policy — the policy-language version, always 2012-10-17.
Effect
Required in every statement — Allow or Deny; an explicit Deny beats any Allow.
Action
What the statement allows or denies — service:operation style like s3:GetObject, granular, wildcards ok (s3:*). NotAction = everything except the listed ops.
Resource
The ARN(s) the statement applies to — in the demo's S3 policy an asterisk meant any S3 resource. NotResource = the complement.
NotAction / NotResource
The complements of Action and Resource — the statement targets everything except what you list.
Condition
Optional element deciding when a statement applies — e.g. restrict by source IP (aws:SourceIp).
Sid
Optional statement ID — a plain comment field for humans, ignored by the policy engine.
ARN structure
arn:aws:service:region:account:resource — colons separate the parts; an empty double-colon means no region applies (IAM users are a global resource).
Session token
The third STS credential, alongside access key + secret — it also carries who you are and the authorization STS verified for the session.
Trusted entity types
Five choices when creating a role: AWS service, AWS account, web identity (OIDC), SAML, or a custom trust policy.
SAML
Trusted-entity type for corporate SSO — users federate in through a SAML identity provider.
Temporary identities
Not every identity is permanent — identities can be permanent or temporary; roles hand out temporary credentials instead of long-term secrets.
Principle of least privilege
Grant only what the task needs — assign it in policy and pair with roles so extra permissions exist only while the work lasts.
Role access via groups
You cannot grant access to a role through an IAM group — the allow-assume permission must go to the user itself.

True / false — quick round

Pick your answer — it highlights green (correct) or red (wrong) and the explanation appears immediately.

The root user can be deleted like any IAM user.

False — permanent identity; it cannot be removed, only protected.

IAM group information can be used to log into AWS.

False — groups are containers for permissions, not login identities.

An explicit Deny in a resource policy beats an Allow from the identity policy.

True — explicit Deny wins over any Allow in policy evaluation.

AWS-managed policies automatically pick up access to newly launched services.

True — that's a benefit of AWS-managed policies; customer-managed ones you maintain yourself.

Roles give you permanent credentials stored in their definition.

False — roles carry NO long-term secrets; STS issues temporary, auto-rotating credentials.

The credential report lists per-user MFA status and access-key last-used dates.

True — that's exactly what it audits; generated in CSV format.

Identity policies grant cross-account access directly.

False — cross-account needs a resource-based policy (or role assumption); identity policies are same-account.

The root user's password policy is set by Amazon and cannot be tuned to your security department's rules.

True — Amazon fixes the root password rules; IAM users follow YOUR password policy.

IAM user password rules, like the root's, are fixed by Amazon.

False — you set the password policy that IAM users comply with.

A freshly created IAM user can exist with zero permissions.

True — exactly why the demos couldn't log in with the new user until a policy or group was attached.

Identity roles and service roles are the only role kinds AWS offers.

False — various kinds exist; those two are just the course's focus right now.

A CloudTrail event record includes the source IP address and the device involved.

True — a record names the principal, account, action, time, source IP, and device info.

With normal IAM permissions, a user can assume every role in the account.

False — the trust relationship gates it; without it in the role's trust policy, assumption is refused.

STS credentials must be rotated manually by an admin.

False — they are temporary and rotate/expire automatically.

Quizzes

1. Authentication vs. authorization — what's the difference?

Show answer
Authentication proves who you are (hotel check-in: passport); authorization decides what you may do (the room card opens your room, maybe gym/pool).

2. What are the root user's password requirements, per the course?

Show answer
Minimum 8 characters, max 128; and per AWS's current rules — include lowercase, uppercase, numbers, symbols (all four), and never equal to the account name or email. Note: the video's "minimum 3 of..." phrasing drops numbers — outdated/incorrect.

3. Identity-based policies come in three forms — which?

Show answer
AWS-managed, customer-managed, and inline policies.

4. When a user assumes a role, what does STS hand back?

Show answer
Temporary security credentials: an access key, a secret access key, and a session token — auto-rotating.

5. How long does CloudTrail keep history by default, and what can you see in one event?

Show answer
~90 days by default; one event shows the principal, account, action, time, source IP, and device info.

6. The IAM credential report — what format, and how long after generation can you download it?

Show answer
CSV; storable and downloadable for up to 4 hours.

7. Who sets the root user's password policy — and can you tune it?

Show answer
Amazon sets it — it is not something you can adjust to suit your security department's needs.

8. A teammate transfers departments — how do their permissions move with them?

Show answer
Via groups: remove them from the old group, add them to the new one — each group carries its policy set, so nothing is retyped per user.

9. Name the five trusted entity types when creating a role.

Show answer
AWS service · AWS account · Web identity (OIDC) · SAML · custom trust policy.

10. What is an ARN, and what changes over your AWS journey?

Show answer
Amazon Resource Name — the structured identifier for every AWS resource; reading its components becomes second nature as you progress.

1. Which element in a statement is required in every IAM policy, and what value beats an Allow?

Show answer
Effect ("Allow"/"Deny") — required in every statement; an explicit Deny beats Allow.

2. What must the Version element be in every IAM policy?

Show answer
"2012-10-17" — the policy-language version, nothing else in practice.

3. In which policy type can you use the Principal element?

Show answer
Resource-based policies only — bucket policies, KMS, SQS... Identity policies attach to the identity and never name a Principal.

4. Name one element that will never appear in an identity-based policy.

Show answer
Principal — identity policies attach to an identity, so there is nothing to name as principal.

5. What does NotAction do in a statement?

Show answer
It inverts the action set — the statement applies to every operation except the listed ones. (NotResource mirrors this for ARNs.)

6. Which element carries a scope like arn:aws:s3:::mybucket/*?

Show answer
Resource — the ARN(s) the statement applies to; NotResource is its complement.

1. A teammate leaves the company Friday. What do you check in the credential report, and what do you clean up?

Show answer
Report: their MFA status, active access keys, last-used dates, last password change. Cleanup: delete the user and keys; use CloudTrail's ~90-day history to review what they did.

2. You want to grant another AWS account access to one specific S3 bucket — which policy type, and why can't an identity policy alone do it?

Show answer
A resource-based policy (bucket policy) — it carries a Principal naming the outside account; identity policies only reach same-account identities (that's why they have no Principal).

3. An intern needs S3 read access for exactly one week — IAM user with attached policy, or role? Why?

Show answer
A role: the intern assumes it via STS, gets auto-rotating temporary credentials; access simply expires after the trust window — no permanent permissions to forget to revoke.

4. A Lambda function must read one specific bucket and nothing else. What do you build?

Show answer
A service role: trust policy Principal = lambda.amazonaws.com, plus a customer-managed policy scoped to that bucket's ARN — never "s3:*" — as execution role.

5. A CI job runs on an EC2 instance and needs S3 access. Access keys baked into the instance?

Show answer
No — attach an instance profile (service role, Principal = ec2.amazonaws.com); the instance fetches auto-rotating STS credentials, no secrets on disk.

6. Security asks: who deleted the S3 bucket last Tuesday, and from which IP? Where do you look?

Show answer
CloudTrail Event history (default ~90-day retention): filter DeleteBucket — the record names the principal, account, time, source IP, and device.

7. Your root user has no MFA. What does the IAM dashboard show when you sign in as root?

Show answer
A security recommendation at the very top of the IAM dashboard — add MFA for the root user (authenticator app: scan the QR code, confirm two consecutive rotating codes, done).

8. An external consultant's AWS account should read exactly one KMS key. Which policy carries the Principal, and what does it name?

Show answer
The key's resource-based (key) policy — its Principal names the consultant's account; their identity policies cannot grant access to your resource.

9. A contractor runs a nightly S3 sync job from an EC2 instance. Design the access.

Show answer
Instance profile (service role trusted to ec2.amazonaws.com) + a customer-managed policy scoped to the sync bucket's ARNs — no access keys on the instance.

10. Auditors demand a 2-year trail of IAM actions. CloudTrail Event history only stretches so far — what's the design?

Show answer
Deliver CloudTrail logs to S3 with the retention you configure — Event history keeps only ~90 days by default; a trail to S3 keeps what the audit needs.
