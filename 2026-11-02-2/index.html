Exam-prep notes (CLF-C02 Domain 3 — Cloud Technology and Services): the CI/CD practice, the four developer tools (CodeCommit, CodeBuild, CodeDeploy, CodePipeline) mapped to their jobs, and a live CloudShell + AWS CLI walkthrough that creates an S3 bucket and uploads a file without touching the console.

Summary

  • What CI/CD is — a widely accepted software development best practice, essential for implementing DevOps: automate code integration and the build-test-deploy functions. Continuous integration = integrating small changes from multiple developers frequently — AWS’s exam-level guidance and the AWS whitepaper both word the cadence as at least once a day; continuous deployment = automating the build, test and deployment functions so changes roll out the moment they are ready. The payoff: makes change easy, everything fast and repeatable and scalable instead of slow/error-prone/inconsistent manual work, and bugs are caught while they are small and simple to fix.
  • The practice nuance the exam also knows — AWS’s own what-is explainers separate continuous delivery (automated build/test/preparation, still an explicit human approval before promoting to production) from continuous deployment (approval automated via pre-configured rules — changes flow with no manual step); some teams deliver several times a day.
  • An example workflow — a dev team downloads code from a central repository, builds and tests locally, and commits to the shared repository; continuous deployment then merges the tested code with the master repository, builds, tests again, packages for deployment, and deploys automatically as soon as it’s ready.
  • The four developer tools and their jobs — CodeCommit: a private Git repository in the cloud, storing source code, binaries, images and software libraries, managing updates from multiple developers (collaboration, change tracking, version history); CodeBuild: a fully managed build service running the commands you define — compile, run tests, produce artifacts ready to deploy (packages = bundles of code ready to deploy, or Docker images); CodeDeploy: automated deployments to EC2 instances, on-premises systems and Lambda (the docs add Amazon ECS, with canary/linear/all-at-once traffic shifting), releasing features quickly, avoiding downtime and manual-process risk; CodePipeline: the continuous-delivery service that models, visualizes and automates the steps required to release software — the end-to-end orchestration, triggered on every code change.
  • Tooling history, verified from the docs today — CodeCommit was closed to new customers on 2024-07-25 and reopened to new customers on 2025-11-25 (per the official documentation history: existing customers used the service as normal throughout) — so a plain presentation of CodeCommit is current today.
  • CloudShell + CLI, hands-on — the browser-based shell has the AWS CLI preinstalled and preconfigured (easiest way to use it): aws --version proves it; then without the console: aws s3 mb s3://mybucket-random (make bucket — S3 names must be globally unique), aws s3 ls (list buckets), echo "My new file" >> file.txt (create a file), cat file.txt, aws s3 cp file.txt s3://bucket (upload), aws s3 ls s3://bucket (confirm the upload). Main concepts

What is CI/CD?
A widely accepted software development best practice and an essential part of implementing DevOps: automate everything, from code integration (merging changes from multiple developers) through build, test and deployment. Small changes applied at least once a day reduce the risk of breaking something and let developers make small, incremental changes — making new features available to customers quickly.
Continuous integration vs continuous deployment
CI: integrating/merging small code changes frequently — the exam cadence is “at least once a day” (AWS’s whitepaper: “at minimum once a day”). CD: automating the build, test and deployment functions. AWS’s explainers split the second C-D: continuous delivery automates build/test/preparation and still requires a manual approval before production, while continuous deployment automates the approval by pre-configured rules — every change flows on automatically. Together, CI/CD are essential DevOps practices.
Why both practices pay off
Automation makes everything fast, repeatable and scalable; manual effort is slow, error-prone and inconsistent. Frequent small changes mean bugs are caught early while they are still small and simple to fix — applying multiple small changes at least once a day makes change easy.
The example CI workflow
A development team works on different parts of the code, downloaded from a central repository to each machine. When ready, they build and test locally; if no bugs are found, the code is committed to the shared code repository — so multiple developers work on the same code and commit their changes.
The continuous deployment flow
After the code is successfully tested it is merged with the master repository; next the code is prepared — built, tested again, and packaged for deployment; finally it is deployed automatically as soon as it is ready. No manual release step sits between the package and production in continuous deployment.
CodeCommit
A central code repository — just like a private Git repository in the cloud. Stores source code, binaries, images and software libraries centrally; manages updates from multiple sources (multiple developers), enables collaboration, tracks and manages code changes, maintains version history.
CodeCommit’s recent history (verified 2026-11-02)
The official documentation history shows: closed to new customers on July 25, 2024 (existing customers could continue as normal, planned investment in security/availability/performance only), then available to new customers again on November 25, 2025 — current today. It remains the plain source-control piece of the pipeline.
CodeBuild
A fully managed build service that runs a set of commands you define: compile code, run tests, produce artifacts ready to deploy. It can reference code stored in your CodeCommit repository to build deployable artifacts — packages or Docker images. A package is simply a bundle of code that’s ready to deploy.
CodeDeploy
Automated deployment service — deploy software to EC2 instances, on-premises systems, and Lambda at its core. Its own docs put it wider: CodeDeploy automates deployments to EC2 instances, on-premises instances, serverless Lambda functions, or Amazon ECS services — with traffic shifted canary, linear or all-at-once on the Lambda/ECS platforms and in-place or blue/green on EC2. Benefit: developers release new features quickly, avoid downtime during deployments, and avoid manual-process risk.
CodePipeline
A continuous-delivery service to model, visualize and automate the steps required to release your software — the automated CI/CD pipeline. Trigger: every change to your code. The code is built (using CodeBuild) and the deployable packages are deployed (using CodeDeploy), making releases fast, consistent and with fewer mistakes. It integrates with lots of other services including CodeCommit, CodeBuild and CodeDeploy.
The four tools mapped onto the workflow
In the example CI/CD workflow: CodeCommit is used to merge or integrate code; CodeBuild builds, tests, and packages the code ready for deployment; CodeDeploy automatically deploys the code in a repeatable way; CodePipeline orchestrates the entire process, managing the end-to-end CI/CD workflow.
The exam tips
Understand what each tool is used for: CodeCommit = source control (collaborate on code, HTML pages, scripts, images, binaries); CodeBuild = compiles source, runs tests, produces packages ready to deploy; CodeDeploy = automates deployments (EC2 instances, Lambda functions, on-premises servers); CodePipeline = manages the workflow (orchestrates the end-to-end build/text/deployment automatically on every code change). And: CloudShell = browser-based shell with the CLI preinstalled; the AWS CLI = command-line tool to manage AWS services.
CloudShell
A browser-based shell for interacting with your AWS account using the AWS CLI — launched from the console’s top-bar icon. The CLI arrives preinstalled and preconfigured, so it’s the easiest way to use the CLI. aws --version proves the install. (The CLI session follows the console’s region — run the walkthrough in a sandbox account.)
The CLI walkthrough, step by step
Task: create an S3 bucket and upload a file — via the CLI in CloudShell instead of the console. aws s3 mb s3://mybucket-123 — make bucket, with a random-suffix name because all S3 buckets need a globally unique name; aws s3 ls lists the account’s buckets (the new one appears); echo "My new file" >> file.txt creates a file with text; ls/cat file.txt check it; aws s3 cp file.txt s3://bucket uploads it; aws s3 ls s3://bucket shows the uploaded file’s name.
Getting help with the CLI
Type the command and append help — the pager opens; Enter moves down; examples live at the very end of the help screen; q exits. Online: search for the AWS CLI command reference, choosing the version 2 reference — documentation organized by AWS service.

Quizzes

1. What are CI and CD — and what cadence does the exam frame use?

Show answer
CI: integrating/merging small code changes frequently — at least once a day (AWS’s whitepaper: “at minimum once a day”). CD: automating the build, test, and deployment functions. Together: the software development best practices essential for implementing DevOps.

2. Name the four AWS developer tools and give each one’s job in one line.

Show answer
CodeCommit — source control: a private Git repository in the cloud; CodeBuild — builds: compiles, tests, produces packages ready to deploy; CodeDeploy — automated deployments: EC2, Lambda, on-premises; CodePipeline — workflow: the end-to-end build/test/deployment automation on every code change.

3. What does CodeBuild produce, and what is a “package”?

Show answer
Artifacts like packages or Docker images, built from code referenced in CodeCommit. A package is simply a bundle of code that’s ready to deploy.

4. Where does CodeDeploy deploy software? (Course answer + the docs’ extra.)

Show answer
Course: EC2 instances, on-premises systems, Lambda. Docs add Amazon ECS services — traffic shifts canary/linear/all-at-once (Lambda/ECS), in-place or blue/green (EC2).

5. Walk the example workflow: what runs locally, what lands in the repository, and what does CD do after the merge?

Show answer
Locally: download from the central repo, build, test. Then: commit to the shared repository. CD: merge with the master repository, build, test again, package for deployment, deploy automatically when ready.

6. In CloudShell, which five CLI commands produce the bucket, the file and the upload?

Show answer
aws s3 mb s3://mybucket-n, aws s3 ls, echo "My new file" >> file.txt (+ls/cat), aws s3 cp file.txt s3://bucket, aws s3 ls s3://bucket.

1. Your team wants a place for source, scripts, binaries AND images — with version history for every change.

2. “Every push must compile, run the full test-suite and stamp a deployable package — and I never want to patch build servers again.”

Show answer

5. In CloudShell you forgot the exact syntax of aws s3 cp.

6. S3 rejects the name you typed for the new bucket — “BucketAlreadyExists”.

Show answer
S3 bucket names are globally unique (page-1’s verified namespace fact): append random numbers/letters (mybucket-123), and for names your account can rely on forever consider the account regional namespace — remember prefix-accountId-region-an only ever belongs to your account.
