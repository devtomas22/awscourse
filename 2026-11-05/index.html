Summary — AWS CloudFormation (Infrastructure as Code)

Exam-focused groundwork page — every point verified against live AWS docs (Nov 9, 2026).

  • The IaC engine. CloudFormation lets you model and set up your AWS resources: you write a template describing the resources you want, and CloudFormation provisions and configures them for you — in dependency order, with no hand-wiring of what depends on what. A stack is the resulting collection, managed as a single unit: delete the stack and all its resources go with it; reuse the template and you replicate the whole environment — consistently, across Regions.
  • Templates — JSON or YAML, several sections, and the only required section is Resources (it must declare at least one resource). Three documented authoring paths: template studio (visual diagram editing), a plain text editor, and the IaC generator, which generates templates from resources provisioned in your account that are not currently managed by CloudFormation. Templates live in S3 (auto-created buckets when you console-upload) or in Git sync — point a stack at a repository branch and CloudFormation monitors it for template changes.
  • The toolbox — intrinsic functions assign values only obtainable at runtime (Ref, Fn::GetAtt, Fn::Sub, Fn::Join, Fn::FindInMap, Fn::Select, Fn::If, Fn::ImportValue among the everyday ones — usable only in resource properties, outputs, metadata, update policies and conditions), and pseudo parameters inject environment values without hard-coding: AWS::Region, AWS::StackName, AWS::AccountId, AWS::Partition, AWS::NoValue (which removes a resource property when returned from Fn::If), and AWS::NotificationARNs — a list you read with Fn::Select.
  • Verified quotas — 500 resources per template (split with nested stacks), 200 parameters, 200 outputs, 200 mappings (each with up to 200 attributes; 255-character names), a 51,200-byte template body in a request (up to 1 MB through an S3 object URL), 2,000 stacks per account per Region, 1,000 stack sets in the administrator account, 2,500 resources in a single nested-hierarchy deployment, 60 dynamic references per template.
  • Stack creation — OnFailure decides what happens if creation fails: DO_NOTHING, ROLLBACK (the default) or DELETE (mutually exclusive with DisableRollback). One documented exception: when a StackSets deployment fails to create a stack instance, CreateStack overrides the default and sets OnFailure to DELETE. Termination protection (stack deletion attempts fail, stack unchanged) is off by default and is set on the root stack for nested stacks.
  • Change sets = the preview step — submit a modified template or parameter values and CloudFormation compares against the stack without changing anything; the change set shows which resources would be added, modified, or deleted and before/after property comparisons. Nothing happens until you execute it (create as many alternatives as you want; executing a change set deletes the stack’s other change sets). They don’t guarantee a successful update — pre-deployment validation catches common causes (syntax, name conflicts, quotas) but runtime conditions can still fail — and the docs’ own best-practice list says to make one before every update.
  • Update behaviors — update with no interruption (physical ID unchanged), with some interruption, or replacement: CloudFormation recreates the resource with a new physical ID, creates the replacement first, re-points references from dependents, then deletes the old. Canonical examples: changing an EC2 instance’s AvailabilityZone or an RDS instance’s Port — and adding or removing a replacement-requiring property triggers replacement even if the value never changed.
  • DeletionPolicy vs UpdateReplacePolicy — DeletionPolicy (default Delete) governs resources left when a stack is deleted or a resource is removed from the template: Retain works for any resource, Snapshot for snapshot-capable ones (e.g. AWS::EC2::Volume), with the exception that AWS::RDS::DBCluster and DBInstance (without DBClusterIdentifier) default to Snapshot. It does not cover replacements — that is UpdateReplacePolicy, which retains or snapshots the old physical instance and executes only when the update behavior is Replacement. Retained things keep billing after leaving CloudFormation’s scope (and an S3 bucket must be emptied before its default deletion succeeds).
  • Drift detection — catches configuration changed outside CloudFormation: a resource has drifted if any actual property value differs from the expected template values, including deleted properties; a stack is DRIFTED if one or more resources drifted; resources that don’t support detection report NOT_CHECKED. Detect on the entire stack or individual resources, then resolve — corrective changes or a documented import operation to pull resources back in sync.
  • StackSets — one operation to create, update, or delete stacks across multiple accounts and Regions from one template (per-stack parameter customization allowed). An administrator account defines the StackSet; target accounts need a trust relationship. Self-managed permissions = you create the IAM roles; service-managed = via AWS Organizations, StackSets creates the roles for you and can turn on automatic deployment to accounts added to the organization later. Operation preferences cover Region order, failure tolerance and concurrency — and a StackSet is a regional resource.
  • Sharing values — a stack can export its Outputs; other stacks in the same account and Region read them with Fn::ImportValue. Reuse grows from there: nested stacks (AWS::CloudFormation::Stack) split a template into reusable pieces under a root stack, modules package resource configurations in the registry, and custom resources (Custom::<name> or AWS::CloudFormation::CustomResource) wire in custom provisioning logic — the service token being their one required property — for resources the built-in types don’t cover.
  • Boots on the ground — cfn-init: declare AWS::CloudFormation::Init in an EC2 resource’s Metadata and the cfn-init helper script (run from user data) fetches and parses that metadata to install packages, write files, and enable/disable plus start/stop services (updating a file leaves a .bak copy). And the docs’ best-practice core: manage all stack resources through CloudFormation, change sets before updates, stack policies, CloudTrail for API logging, code review + revision control for templates, regular drift detection — and never embed credentials.

Main concepts — templates, stacks, updates, and the reuse toolbox

Stacks: create, update, delete
A template describes your resources; creating the stack provisions the actual resources in dependency order; updating it applies your changes (rehearsable through change sets); deleting the stack deletes the resources. This unit-of-management idea is why the docs’ opening pitch is: easily manage a collection of resources as a single unit, quickly replicate infrastructure, and control and track changes including rolled-back updates.
Template anatomy and the required section
Sections: format version, Description, Parameters, Mappings, Conditions, Resources — the only required section, with at least one resource — plus Outputs. Format: JSON or YAML. Validate cheaply before deploying: the validate-template CLI command or console check (syntax-level) alongside companion tools (CloudFormation Linter, Guard). Templates can carry modules (reusable resource configurations registered in the CloudFormation registry — 100 modules per account and Region, 100 versions each).
Authoring paths (docs-current)
Template studio — edit templates and view their resources in a visual diagram. Text editor — raw JSON/YAML. IaC generator — generate templates from resources provisioned in your account that are not currently managed by CloudFormation (works with the resource types the Cloud Control API supports in the Region). Plus Git sync: specify a repository and branch instead of uploading — CloudFormation monitors the branch for template changes.
Intrinsic functions — the everyday set
Ref (parameter or logical-resource value), Fn::GetAtt (attributes of resources you own), Fn::Sub (string interpolation incl. pseudo parameters in ${}), Fn::Join, Fn::Split, Fn::Select, Fn::FindInMap (Mappings), Fn::If (Conditions; returns AWS::NoValue to drop a property), Fn::ImportValue (cross-stack outputs). The reference also lists Fn::Base64, Fn::Cidr, Fn::GetAZs, Fn::Length, Fn::ForEach, Fn::ToJsonString and Fn::Transform. Scope rule: resource properties, outputs, metadata, update policy attributes and condition expressions — that’s it.
Pseudo parameters — portable templates
AWS::AccountId (account id — think IAM policies and account-scoped ARNs), AWS::Region (deployment Region), AWS::StackName, AWS::Partition (ARN partition: aws, aws-cn, aws-us-gov…), AWS::NotificationARNs — the odd one out, it’s a list of SNS ARNs for stack events, consumed with Fn::Select — and AWS::NoValue, which removes the corresponding resource property when returned from Fn::If (the conditional-property idiom). Reference via Ref or ${AWS::…} inside Fn::Sub.
The verified quota table
500 resources per template; 200 parameters, 200 outputs, 200 mappings with up to 200 attributes each; mapping/parameter/output names 255 characters; template body 51,200 bytes in a request or 1 MB in an S3 object; 2,000 stacks per account per Region; 1,000 stack sets; 2,500 resources in one nested-stack-hierarchy deployment (an older hierarchy may total more — the cap is per single deployment operation); 60 dynamic references per template; 100 hooks per account/Region; cfn-signal and custom-resource responses capped at 4,096 bytes.
OnFailure and termination protection
CreateStack’s OnFailure: DO_NOTHING | ROLLBACK | DELETE — default ROLLBACK; you may specify OnFailure or DisableRollback, never both. The exception: when StackSets deploys a stack instance and creation fails, the CreateStack call overrides the default and sets OnFailure to DELETE. Termination protection: a delete attempt on such a stack fails and the stack remains unchanged; deactivated by default; on nested stacks it’s managed at the root stack.
Change sets — the rehearsal
Create → compare (no changes applied) → view what would be added, modified, or deleted with before/after property comparisons → execute when satisfied. Multiple change sets per stack for evaluating alternatives; after you execute one, all of the stack’s change sets are removed (they’re no longer applicable). Honest caveat from the docs: change sets don’t guarantee successful updates — pre-deployment validation catches syntax errors, name conflicts and quota issues, but runtime conditions (custom-resource logic, service constraints) can still fail during execution. Express mode (--deployment-config {"mode": "EXPRESS"}) completes resource operations as soon as configuration is applied.
Update behaviors in one table
Update with no interruption: same physical ID, no disruption (e.g. CloudTrail trail settings). Update with some interruption: e.g. EC2 instance reconfigured mid-update. Replacement: new physical ID — replacement created first, references re-pointed, old resource deleted. Which behavior a property has is documented per resource type in the AWS resource and property types reference — EC2 AvailabilityZone and RDS Port are the docs’ replacement examples, the latter with a prepared plan: snapshot first, think about app interruption, then restore. Adding or removing a replacement-requiring property triggers replacement even if the real value never changes.
DeletionPolicy and UpdateReplacePolicy, disentangled
DeletionPolicy — fires when the stack is deleted or a resource is removed from the template on update. Options: Delete (default), Retain (any resource — even a nested stack, S3 bucket or EC2 instance; the docs’ recommended route before taking resources out of CFN management), Snapshot (snapshot-capable resources like AWS::EC2::Volume). Exceptions to the default: RDS DBInstance (without DBClusterIdentifier) and DBCluster default to Snapshot; and an S3 bucket must have all its objects deleted for deletion to succeed. UpdateReplacePolicy — fires only when an update causes a replacement: retain or snapshot the old physical instance; the old resource or snapshot keeps incurring costs and leaves CloudFormation’s scope.
Drift — detection and the way back
Expected values = stack template + parameters; actual = what the service currently holds. Changed or deleted properties mark the resource drifted; any drifted resource marks the stack DRIFTED. Statuses: drifted / not drifted (in-sync) plus NOT_CHECKED for resources without drift support. Check the whole stack or individual resources. Resolution: corrective action — edit resources so they agree with the template — or the documented import operation for resources that left management. Best practice: use drift detection regularly.
StackSets — concepts and permissions
A StackSet is a container for stacks deployed to selected target accounts and Regions from one template — one operation to create, update or delete them all; operation preferences set Region order, failure tolerance before stopping, and account concurrency. Administrator account owns the StackSet (for service-managed: management or delegated admin account); target accounts need a trust relationship first. Self-managed: you create the IAM roles; deploy to any account where you can create roles. Service-managed: AWS Organizations — StackSets creates the roles, deploys to org accounts, and supports automatic deployments to accounts added to the organization in the future (with QUEUED operations for the catch-up). The StackSet itself is regional — created in one Region, managed there.
Cross-stack references
Stack A declares an Output with a Export name; CloudFormation exports the value to the account-Region. Stack B reads it with Fn::ImportValue and CloudFormation retrieves it automatically on create/update. Same account and Region only — for other accounts/Regions, replicate the resource (this is StackSets territory). The docs contrast exports with nested stacks, which pass values internally instead.
Nested stacks, cfn-init, custom resources
Nested stacks: extract repeated configurations into dedicated templates and reference them with the AWS::CloudFormation::Stack resource type; hierarchies nest deeper, all under the root stack (each nested stack has a parent; the top-level is both). cfn-init: put AWS::CloudFormation::Init in an EC2 resource’s Metadata; the cfn-init helper script — typically invoked from user data — reads the metadata and installs packages, writes files, enables/disables and starts/stops services (updated files keep a .bak). Custom resources: type AWS::CloudFormation::CustomResource or Custom::MyName; one required property — the service token (a Lambda function or SNS topic) that CloudFormation calls on create, update (if changed) and delete; use them for resources unavailable as built-in types or bespoke provisioning logic.
Best practices (the docs list, compressed)
Shorten the feedback loop; organize stacks by lifecycle and ownership; use cross-stack references and StackSets; verify quotas up front; reuse templates and modules; adopt IaC practices — never embed credentials (use dynamic references/Secrets Manager), AWS-specific parameter types, parameter constraints; manage all stack resources through CloudFormation; create change sets before updating; stack policies to protect resources; CloudTrail for all CFN API calls; code reviews and revision control; regular drift detection; rollback triggers for automatic recovery; templates from existing resources with the IaC generator; visual edits with template studio.

Quizzes

1. Create a stack — what happens on failure, and what’s the StackSets quirk?

Show answer
OnFailure: DO_NOTHING, ROLLBACK (default), DELETE (never together with DisableRollback). Quirk: if a StackSets deployment fails to create a stack instance, CreateStack overrides the default and uses DELETE.

2. What does a change set give you — and what does it NOT give you?

Show answer
A preview: which resources would be added, modified, or deleted, with before/after property comparisons — nothing applied until you execute. It does not guarantee success: validation catches syntax/conflicts/quotas, but runtime conditions can still fail.

3. Name the three update behaviors and what a replacement does.

Show answer
No interruption (physical ID unchanged), some interruption, replacement: a new physical ID — CloudFormation creates the replacement first, re-points dependent references, then deletes the old resource. EC2 AvailabilityZone and RDS Port are the docs’ examples.

4. DeletionPolicy defaults worth warning teammates about?

Show answer
Default Delete; Retain for anything you’ll reuse; Snapshot for snapshot-capable resources — with AWS::RDS::DBCluster and DBInstance (without DBClusterIdentifier) defaulting to Snapshot. And S3 buckets must be emptied before deletion succeeds.

5. What are drift statuses and the two resolution paths?

Show answer
Resources: DRIFTED / in-sync (not drifted); undetectable resources NOT_CHECKED; the stack is DRIFTED if ≥1 resource is. Fix: corrective action (edit resources to agree with the template) or the import operation.

6. StackSets permission models in one breath?

Show answer
Self-managed: you create the trust IAM roles; deploy to any account where you can create roles. Service-managed: AWS Organizations — StackSets creates the roles, deploys to org accounts, and can auto-deploy to accounts added later. The StackSet itself is regional.

1. An ops engineer edited a prod database by hand after a storm; now your updates are risky.

Show answer
Run drift detection (whole stack, then the resource): if it’s DRIFTED, resolve by corrective action or the import operation, then keep updates predictable again. Going forward: regular drift checks + stack policies.

2. Compliance wants a preview of next week’s stack upgrade in writing.

Show answer
Create a change set: it lists added/modified/deleted resources and before/after property comparisons without touching the stack — execute only when the plan is approved (keep alternates as extra change sets).

3. A 600-resource monolith template just hit a wall.

Show answer
Quota: 500 resources per template. Split by lifecycle/ownership into multiple templates — nested stacks (AWS::CloudFormation::Stack) or plain sibling stacks connected by exports + Fn::ImportValue.

4. You need the same baseline stack — VPC, buckets, roles — in 12 accounts and 3 Regions.

Show answer
StackSets: one operation, one template, per-account parameter customization. In an organization use service-managed permissions and turn on automatic deployments so future accounts get the baseline too.

5. The team wants an S3 bucket to survive stack deletion, but the database snapshot kept too.

Show answer
Set DeletionPolicy: Retain on the bucket (empty it first — else deletion fails), and remember RDS DBInstance/DBCluster default to Snapshot anyway. For update-time replacements of such resources, set UpdateReplacePolicy.

6. Bootstrap an EC2 fleet with packages, config files and running services — from the template.

Show answer
AWS::CloudFormation::Init metadata + the cfn-init helper script invoked from user data: installs packages, writes files, starts/stops services (and signals completion via cfn-signal when configured).
