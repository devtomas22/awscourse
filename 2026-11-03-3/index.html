Summary — asynchronous messaging (SNS / SQS)

Groundwork page — no transcript; every point verified against live AWS docs today.

  • What asynchronous messaging is — producers and consumers communicate without waiting on each other: messages are stored until consumed. The docs’ definition of a message queue: a form of asynchronous service-to-service communication used in serverless and microservices architectures; messages are stored on the queue until they are processed and deleted. The payoff is decoupling: batching jobs, absorbing bursts, and keeping failures local — a slow or down consumer never stops the producer.
  • Amazon SQS in one card — a fully managed, pull-based queuing service: producers send messages to a queue, consumers poll for them with SendMessage, ReceiveMessage and DeleteMessage, then delete what they processed. Two queue types: Standard (the default) and FIFO.
  • Standard queues (the default type) — support a nearly unlimited number of API calls per second; delivery is at-least-once (every message is delivered at least once, though a message may occasionally be delivered more than once), and ordering is best-effort (SQS attempts send-order but doesn’t guarantee it). Practical rule: keep consumers idempotent or dedupe by message ID; order-sensitive work needs FIFO.
  • FIFO queues — exactly-once processing: FIFO queues deliver each message once and keep it available until you process and delete it; processing the same message multiple times will not affect the system’s state. Strict ordering. Naming: a FIFO queue’s name must end with the .fifo suffix (it counts toward the 80-character queue-name quota). High-throughput mode supports up to 3,000 messages per second with batching, or up to 300 messages per second for send, receive and delete operations (docs).
  • Verified SQS numbers — max message size 1,048,576 bytes (1 MiB), 1-byte minimum (larger payloads: the SQS Extended Client Library put the payload in S3) — the old 256 KB figure is outdated for SQS. Retention: default 4 days, minimum 60 seconds (1 minute), maximum 1,209,600 seconds — 14 days.
  • Visibility timeout and polling — when a consumer receives a message it becomes hidden from other consumers for the visibility timeout: default 30 seconds, maximum 12 hours; setting VisibilityTimeout to 0 seconds terminates the timeout so another consumer can take the message. Short polling (default) responds immediately but samples a subset and can return empty responses; long polling (ReceiveMessage wait time > 0, maximum 20 seconds) waits for messages to arrive — fewer empty responses, lower cost.
  • Dead-letter queues — messages that keep failing move out of the hot path via a redrive policy whose maxReceiveCount sets how many times a consumer can receive a message from the source queue before it moves to the dead-letter queue (docs).
  • Amazon SNS in one card — a fully managed pub/sub push service: you publish to a topic (the logical access point / communication channel) and subscribers receive copies. It spans Application-to-Application (A2A) and Application-to-Person (A2P) messaging; subscriber endpoint types per the docs: Amazon SQS, Lambda, HTTP(S), Email, Mobile push, Mobile text (SMS), Amazon Data Firehose, and service providers like Datadog, MongoDB and Splunk.
  • SNS mechanics — subscription confirmation: HTTP(S) endpoints, email addresses and cross-account AWS resources must confirm their subscription before receiving (subscriptions sit PendingConfirmation up to 30 days). Filter policies: a JSON object on the subscription selecting which subset of published messages that subscriber receives. Message attributes: structured metadata (timestamps, geospatial data, signatures, identifiers). Raw message delivery: for SQS subscribers, SNS metadata is stripped and the message is sent as is.
  • Verified SNS numbers + FIFO topics — the Publish API caps messages at 256 KiB (262,144 bytes) by default; AWS whats-new (Sept 18, 2026) raised SNS payloads up to 1 MiB — a 4x increase — with a per-topic MaximumMessageSize configuration. SNS FIFO topics (First-In-First-Out) deliver in order with deduplication, pairing with SQS FIFO queues.
  • Fan-out and choosing — the fan-out pattern: one SNS topic delivering copies of each message to multiple SQS queues so consumers process independently and asynchronously (docs page title: “Fanout Amazon SNS notifications to Amazon SQS queues for asynchronous processing”). Choosing rule: SQS when one producer feeds one worker pool that pulls at its own pace (buffering, bursts, retries, DLQs); SNS when one event must reach many endpoints immediately (email, SMS, Lambda, push); SNS fan-out into SQS when you need immediate broadcast plus durable per-consumer buffers with independent pacing.

Main concepts — SNS / SQS

Why decouple at all
Direct endpoint-to-endpoint calls couple lifecycles: a slow or down consumer stalls the producer. Asynchronous messaging stores messages until consumed, so each side scales, fails and deploys independently — batching jobs, riding out bursts, and retrying later. In AWS, the two primitives are SQS (queuing) and SNS (pub/sub).
The message-queue definition, verbatim
Docs: a message queue is a form of asynchronous service-to-service communication used in serverless and microservices architectures; messages are stored on the queue until they are processed and deleted. Producers push without waiting; consumers pull at their own rhythm.
Amazon SQS anatomy
Fully managed, pull-based: producers SendMessage into a queue; consumers ReceiveMessage, process, then DeleteMessage. Two types: Standard (default) and FIFO (name ends in .fifo).
Standard queue semantics
Nearly unlimited API calls per second; at-least-once delivery — a message may occasionally be delivered more than once (highly distributed architecture); best-effort ordering — order attempted, never guaranteed. Hence: idempotent consumers or message-ID dedupe; order-critical work goes FIFO.
FIFO queue semantics
Exactly-once processing — each message is delivered once and kept available until processed and deleted; processing the same message multiple times won’t affect system state. Strict ordering. Verified today: names must end .fifo; high-throughput mode = 3,000 msg/s with batching (or 300 msg/s per operation).
The SQS numbers card
Max message size 1 MiB (1,048,576 bytes) — 256 KB is outdated (Extended Client Library for bigger payloads). Retention: default 4 days, min 60 seconds, max 14 days (1,209,600 s). Visibility timeout: default 30 s, max 12 hours.
Visibility timeout mechanics
Receiving hides a message from other consumers for the visibility timeout. Processed? DeleteMessage removes it. Slower than expected? Extend the timeout (docs suggest starting shorter, e.g. minutes). Failed? VisibilityTimeout = 0 releases it for another consumer — or let the DLQ redrive policy catch poison messages.
Short vs long polling
Short polling (default): immediate response, samples a subset — empty responses possible. Long polling: ReceiveMessage wait > 0 (max 20 seconds) — the request waits for messages, fewer empty responses and lower cost. Default to long polling for steady consumers.
Dead-letter queues and redrive
A redrive policy names a DLQ and a maxReceiveCount — the number of receive attempts allowed before the message moves to the dead-letter queue. Keeps poison messages from spinning in the hot path; DLQ retention follows its own settings.
Amazon SNS anatomy
Fully managed push pub/sub: publish to a topic (logical access point), subscribers receive copies. A2A: SQS, Lambda, HTTP(S), Amazon Data Firehose, service providers (Datadog, MongoDB, Splunk). A2P: email, mobile text (SMS), mobile push — one service spans both.
Subscription confirmation
HTTP(S) endpoints, email addresses and cross-account AWS resources confirm the subscription (the email route is the one today’s monitoring-alarm demo used) before messages flow; unconfirmed subscriptions sit PendingConfirmation up to 30 days.
Filter policies and message attributes
Publishers attach message attributes — structured metadata like timestamps, geospatial data, signatures, identifiers. A subscriber assigns a filter policy (a JSON object) to its subscription so it only receives the subset of messages it cares about — fan-out with per-subscriber precision.
Raw message delivery
SNS wraps messages in its own JSON envelope by default. For SQS (and other) subscribers, enabling raw message delivery strips the SNS metadata — the message is sent as is, so the queue holds exactly what the publisher sent.
The verified SNS numbers
Publish API default cap: 256 KiB (262,144 bytes); AWS whats-new Sept 18, 2026: payloads up to 1 MiB — a 4x increase — configurable per topic (MaximumMessageSize). Message attributes count toward the size restriction.
SNS FIFO topics
First-In-First-Out topics deliver messages in order with deduplication, integrating with SQS FIFO queues — the pair to choose when a broadcast must keep strict ordering end to end.
Choosing: SQS, SNS, or fan-out
One producer → one worker pool, pull at own pace, buffer bursts, retry with DLQ → SQS. One event → many endpoints immediately (email, SMS, Lambda, push) → SNS. Broadcast AND durable buffers → fan-out: topic pushes copies into several SQS queues, each with its own consumers, pacing, filter policy and raw delivery.

SQS or SNS: one-to-one
Pull-based buffering with consumers pacing themselves — bursts absorbed, failures retried — is SQS territory.
SQS or SNS: one-to-many
Pushing the same message to many endpoints at once is SNS territory.
SQS or SNS: broadcast + durability
SNS for immediate copies with SQS queues behind it for durable per-consumer buffers — the fan-out combination.
Producer
The side that sends messages into a queue or publishes to a topic — it never waits on the consumer.
Consumer
The side that polls a queue (SQS) or receives pushes (SNS), processes the message, then deletes/acks it.
DeleteMessage
The consumer’s finishing move in SQS — processed messages are removed so they aren’t redelivered.
Duplicate handling
At-least-once means occasional duplicates: keep processing idempotent or dedupe on the message ID.
Why buffer with a queue
Absorb bursts: producers keep sending while consumers scale independently — neither side fails when the other slows down.
Push vs pull cost angle
Pull (SQS): consumers spend cycles polling (long polling softens it); push (SNS): the service delivers straight to each endpoint.
When order really matters
Pair an SNS FIFO topic with SQS FIFO queues (the .fifo suffix on both) so consumers see messages in send order end to end.
Decoupling catchphrase
Asynchronous messaging keeps failures local — a slow or down consumer never stops the producer.

Quizzes

1. Standard vs FIFO — the one-breath comparison?

Show answer
Standard (default): nearly unlimited API calls/sec, at-least-once delivery (occasional duplicates), best-effort ordering. FIFO: exactly-once processing, strict order, .fifo name suffix, high-throughput mode (3,000 msg/s with batching / 300 per operation).

2. The SQS numbers to memorize?

Show answer
Max message 1 MiB (1,048,576 bytes) — 256 KB outdated; retention: 4 days default, 60 seconds minimum, 14 days max; visibility timeout: 30 s default, 12 h max.

3. Consumers keep getting empty poll responses — what changes that?

Show answer
Long polling: set the ReceiveMessage wait time above 0 (max 20 seconds) — the request waits for messages, so empty responses drop and cost falls.

4. What gets a poison message into the dead-letter queue?

Show answer
The redrive policy with its maxReceiveCount: once the message has been received that many times from the source queue without being deleted, it moves to the DLQ.

5. Which SNS subscribers must confirm their subscription — and for how long can a subscription sit pending?

Show answer
HTTP(S) endpoints, email addresses, and AWS resources in other accounts must confirm before receiving; subscriptions stay PendingConfirmation up to 30 days (docs).

6. What makes fan-out work — and why do you add SQS queues under an SNS topic?

Show answer
SNS natively copies each published message to every subscribed queue. The queues add durable buffering: each consumer processes independently at its own pace, with its own retention, DLQ and raw-delivery/filter settings.

1. Payment events must be processed in order, never twice. What do you build?

Show answer
An SQS FIFO queue (name ends .fifo): exactly-once processing and strict order. Need more than 300 msg/s? Enable high-throughput mode — up to 3,000 msg/s with batching.

2. One order event must reach an email address, an SMS user and a Lambda function instantly.

Show answer
SNS: one publish to the topic pushes to every subscribed endpoint — Application-to-Person (email, SMS/mobile push) and Application-to-Application (Lambda) in one hop.

3. Traffic spikes at 3 a.m.; consumers were overwhelmed; some messages keep failing no matter what.

Show answer
Scale consumers against an SQS buffer so bursts queue up instead of hitting servers; configure a dead-letter queue via a redrive policy (maxReceiveCount) so persistent poison messages leave the hot path.

4. Three microservice queues listen to the same topic — but each needs only “order-cancelled” events.

Show answer
SNS fan-out + filter policies: each subscription carries a JSON filter policy (keyed on message attributes) so it receives only the subset it cares about.

5. Workers report seeing the same message a few times a week. Why — and what changes?

Show answer
That’s at-least-once delivery on standard queues: occasional duplicate delivery is by design. Make consumers idempotent or dedupe on the message ID; switch to FIFO when exactly-once is non-negotiable.

6. Your SQS subscriber chokes on SNS’s JSON wrapper around each message.

Show answer
Enable raw message delivery for that subscription: SNS metadata is stripped and the message arrives as is — exactly what the publisher sent.
