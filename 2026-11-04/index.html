Summary — CloudWatch Events + EventBridge Scheduler (SNS/SQS patterns)

Exam-focused groundwork page — every point verified against live AWS docs (Nov 9, 2026).

  • One service, many doors. Amazon EventBridge is the serverless event-bus service wiring AWS, SaaS partners and home-grown apps together (event-driven architecture). Today’s lineup: a default event bus that automatically receives AWS service state-change events (250+ services send them; S3 sends its data-plane events once you enable EventBridge on the bucket), Custom Event Bus - Classic (launched July 2019 — routes with rules and targets), the new Custom Event Bus (launched September 2026 — routes to subscribers, with built-in retention), plus partner event buses for SaaS integrations — with EventBridge Pipes alongside for point-to-point streaming.
  • The new Custom Event Bus — one team runs it, many accounts use it: shared through AWS RAM with managed permissions, consumers each attach their own subscribers (filters + one target per subscriber), the bus retains every event for 1–365 days, delivery can be ordered (FIFO) within an event group, new subscribers replay or catch up via a starting position, publishes dedupe within a 5-minute window, and PutRawEvents accepts Avro, Protobuf and raw bytes — while universal targets call any state-changing AWS API directly. Docs guidance: for new applications, start with this bus.
  • Classic bus mechanics — a rule specifies which events go to which targets; one rule fans out to multiple targets in parallel (two rule types: event-pattern matching and scheduled). Verified quotas: 300 rules per event bus, 5 targets per rule (not adjustable), event patterns up to 2,048 characters, up to 100 event buses per account.
  • Event anatomy — every event is a JSON envelope: source, detail-type, detail (the three required for PutEvents), plus id (the UUID that traces events through rules to targets), time, region, account, resources. Examples: aws.ec2 / EC2 Instance State-change Notification; aws.cloudwatch / CloudWatch Alarm State Change — whose delivery to EventBridge AWS guarantees.
  • Input transformation — the classic input transformer defines up to 100 variables pulled from the original event with JSONPath and rewrites the payload into an input template before the target sees it; the new bus transforms with JSONata expressions (including target parameters like SqsParameters.MessageDeduplicationId).
  • Scheduled rules are legacy; Scheduler is the recommendation. Classic scheduled rules take a six-field cron (minutes, hours, day-of-month, month, day-of-week, year; ? must replace * in one of the two day fields; L/W/# wildcards; nothing faster than 1 minute) or a rate expression — running in UTC. The docs now say plainly: use EventBridge Scheduler.
  • EventBridge Scheduler — a separate serverless scheduler: one-time at(yyyy-mm-ddThh:mm:ss) schedules plus cron and rate set in any time zone with automatic daylight-saving handling, all invoking targets with 60-second precision; a flexible time window (Mode FLEXIBLE with a maximum window in minutes, e.g. 15) disperses invocations to improve reliability. Targets: templated (SQS SendMessage, Lambda Invoke, Step Functions…) or the universal target reaching 270+ AWS services and 6,000+ API operations. Verified quotas: 10,000,000 schedules per Region, CreateSchedule 5,000 TPS, invocations 1,000 TPS; pricing 14,000,000 invocations/month free, then $1.00 per million.
  • Delivery you can trust — rule targets retry up to 185 times over 24 hours with exponential backoff and jitter by default; after that events are dropped unless a dead-letter queue is attached — and EventBridge DLQs must be standard SQS queues, each message carrying RULE_ARN, TARGET_ARN and ERROR_CODE. Scheduler keeps its own retry policy (max age 60–86,400 seconds, up to 185 attempts) and delivers a JSON dead-letter event to the SQS DLQ once retries are exhausted.
  • The SNS/SQS integration playbook — a rule target list that includes SQS (standard, fair and FIFO queues — a FIFO target takes its message group via SqsParameters), SNS topics, Lambda, Step Functions, SSM, Kinesis, Firehose, CodePipeline/CodeBuild and API destinations. Practical shapes: rules → per-consumer SQS queues for durable pacing with DLQs; rule → SNS topic for humans or when one rule must reach more than its 5 target slots; Scheduler → SQS/Lambda for timezoned jobs.
  • Industry-standard setups — alarm state-change rules on aws.cloudwatch feed SNS for email/chat ops (with SNS filter policies trimming volume); S3 event rules route Object Created etc. to per-team SQS buffers; the platform team runs one shared bus with per-account subscribers (new bus) instead of editing routing for every team; ordered per-account processing = FIFO event-group subscribers into SQS FIFO; and because classic events bill in 64-KB chunks, big payloads stay out of the event: store in S3, publish a pointer event.

Main concepts — EventBridge, Scheduler, and the messaging patterns

From CloudWatch Events to EventBridge
The event-bus machinery — rules matching events, targets receiving them, schedules firing them — grew up as CloudWatch Events and was relaunched as EventBridge in July 2019 (today’s pricing page dates the “Custom event bus - Classic” to July 2019). The old scheduled-events documentation now lives inside the EventBridge user guide marked (legacy) with a pointer to Scheduler — which is why today’s lesson names both. One naming trap: buses, rules and targets are EventBridge features, not CloudWatch monitoring console tabs.
The 2026 bus lineup
Default bus: exists in every account, automatically receives AWS service state-change events (250+ AWS services send events; S3 sends data-plane events only after you enable EventBridge on the bucket; alarm state-change events arrive with guaranteed delivery). Partner event buses: SaaS integrations. Custom Event Bus - Classic (July 2019): you route with rules and targets. Custom Event Bus (September 2026): subscribers + retention, recommended for new applications. Plus Pipes — point-to-point, one source to one target with optional filter/transform/enrich, often used with a bus as its target.
The new Custom Event Bus, in one card
Publish with PutEvents (JSON) or PutRawEvents (Avro, Protobuf, raw bytes); the bus routes each event to every subscriber whose filters match and keeps a copy for a retention period you set (1–365 days). Share with AWS RAM managed permissions (e.g. subscribe-only); each consumer account owns its subscribers (you can revoke any with RevokeResource). Ordered (FIFO) delivery within an event group, per subscriber; new or paused subscribers resume from a starting position over retained events; publish-time deduplication within a 5-minute window, by content or by a key you supply. Targets: one per subscriber (create one subscriber per target), including universal targets that call any state-changing AWS API.
Classic rules and their verified quotas
A rule on a bus specifies which events go to which targets; a single rule sends an event to multiple targets in parallel; two types — event-pattern rules (match on event data as events arrive) and scheduled rules (legacy). Numbers from today’s quota page: maximum 300 rules per event bus (adjustable; 100 in a couple of regions), 5 targets per rule (not adjustable), event pattern 2,048 characters max, 100 event buses per account (adjustable).
Event JSON anatomy
Fields on every event: version, id (UUID — use it to trace events as they move through rules to targets), detail-type (combined with source it determines the detail shape), source, account, time, region, replay-name (on replays), resources (ARN array), detail (the JSON object). Your own PutEvents publishes require exactly three fields: source, detail-type, detail. Sample pairs: aws.ec2 → “EC2 Instance State-change Notification”; aws.cloudwatch → “CloudWatch Alarm State Change”.
Matching: event patterns
Rule patterns filter on the envelope and the payload — source, detail-type, region, and content inside detail. A pattern is constrained to 2,048 characters; docs support wildcard matching in patterns, and CloudWatch alarm events can carry an alarmTags object to make pattern filtering easier. Filter early (at the rule or the new-bus subscriber) so downstream queues stay lean — the industry pattern.
Classic targets and the SQS/SNS shapes
Target catalog includes Amazon SQS queues (standard, fair, and FIFO — SqsParameters supplies the message group), Amazon SNS topics, Lambda, Step Functions (async), EC2, ECS, SSM Run Command/Automation/OpsItem, Kinesis streams, Firehose, CodePipeline, CodeBuild, SageMaker pipelines, Redshift Data and API destinations (call external HTTP APIs through authenticated connections). EventBridge needs an IAM execution role; the target’s resource policy must grant the action (e.g. sqs:SendMessage, sns:Publish).
Input transformer (classic) and JSONata (new bus)
Input transformer: define up to 100 variables, each a JSONPath into the original event, then interpolate them into an input template with <variable-name> placeholders — the transformed event replaces the original at the target. Predefined variables exist (aws.events.rule-arn, …). Note: not all JSONPath syntax is supported (no wildcards * or forward slashes in paths). The new Custom Event Bus uses JSONata expressions for subscriber transforms and target parameters.
Scheduled rules (legacy): cron and rate
Cron: six required fields — minutes (0–59), hours (0–23), day-of-month (1–31), month (1–12 / JAN-DEC), day-of-week (1–7 / SUN-SAT), year (1970–2199) — wildcards , - * /; L = last day of month/week, W = weekday nearest (e.g. 3W), # = nth weekday of the month. You cannot use * in both day fields — put ? in one. Nothing faster than once per minute. Docs examples run in UTC (cron(15 10 ? * 6L 2019-2022) = 10:15 UTC on the last Friday). Rate: rate(value unit). The docs tag this approach legacy and point to Scheduler.
EventBridge Scheduler — the modern way to schedule
A separate, serverless scheduler. Three schedule types: rate-based, cron-based, and one-time — at(yyyy-mm-ddThh:mm:ss), which ignores StartDate/EndDate. Every schedule declares a time zone (cron and one-time times evaluate in it; daylight-saving changes are adjusted automatically) and all types invoke targets with 60-second precision. A flexible time window (Mode FLEXIBLE, maximum window in minutes — e.g. 15) lets Scheduler spread the invocation across the window — reliability through dispersion. Templated targets cover common APIs (Lambda Invoke, SQS SendMessage, Step Functions); the universal target parameterizes any state-changing API — EventBridge Scheduler pages put it at 270+ AWS services and 6,000+ API operations.
Scheduler numbers worth memorizing
10,000,000 schedules per Region default (adjustable toward billions), CreateSchedule 5,000 TPS, invocation throttle 1,000 TPS. Retry policy: MaximumEventAgeInSeconds 60–86,400 (up to 24 hours) and MaximumRetryAttempts 0–185 with exponential backoff. Failed invocations land a JSON dead-letter event (invocation details + the target’s response) in a configured SQS DLQ. Pricing: 14,000,000 invocations per month free across Regions, then $1.00 per million (example: 20M invocations → (20M−14M) × $1.00 = $6.00).
Delivery reliability on rules: retries and DLQs
By default EventBridge retries an event to a target for 24 hours and up to 185 times with exponential backoff and jitter. After the last attempt the event is dropped — unless the target has a dead-letter queue. DLQs for rules must be STANDARD SQS queues; each DLQ message carries RULE_ARN, TARGET_ARN and ERROR_CODE attributes, and there are documented permission grants plus a documented resend flow. On the new bus, the subscriber’s OnFailureConfiguration.Arn names the SQS queue that receives one record per event that exhausted retries.
SNS and SQS in the EventBridge patterns
Rule → SQS queue: durable per-consumer buffering — each queue drains at the consumer’s pace with its own retention, batching, retries and DLQ (the Nov 3 messaging page covers the queue semantics). Rule → SNS topic: instant multi-endpoint push (email, SMS, chat, more queues) and the way around the 5-targets-per-rule cap. Rule → SQS FIFO: ordered delivery when it matters. Scheduler → SQS/Lambda: timezoned cron with DLQ accountability. SNS filter policies keep per-subscriber volume controlled even when one topic carries many event types.
Industry-standard setups (the synthesis)
Alarm ops: CloudWatch alarm state-change rules → SNS topic → email/chat (filter on state=ALARM). Upload pipelines: enable EventBridge on the S3 bucket; route Object Created rules into per-consumer SQS queues (DLQs on). Timezoned jobs: Scheduler cron with the team’s time zone + flexible window, targets Lambda or SQS. Multi-team bus: one Custom Event Bus shared via RAM — consumers own subscribers; the platform team never edits routing. Order: publish with a group key, FIFO subscriber → SQS FIFO. Cost hygiene: classic events bill in 64-KB chunks — store large payloads in S3 and publish pointers.
Pricing landscape (verified today)
Classic bus (64-KB chunks — one event each): AWS management events ingest free; custom/partner events $1.00/M ingest; delivery cross-account $1.00/M; partner events $0.05/M delivery. Pipes $0.40/M requests; API destinations $0.20/M; archive processing $0.10/GB + storage $0.023/GB; replayed events $1.00/M. Schema Registry free; Schema Discovery 5M events/month free. Scheduler: 14M invocations/month free, then $1.00/M. New Custom Event Bus (Sept 2026): GB-priced — ingress $0.18/GB (first 5,000-GB tier), egress $0.05/GB, event evaluation $0.15/M when configured, storage $0.08/GB beyond the default retention.

Quizzes

1. What are the two rule types on the classic bus, and what does a rule actually do?

Show answer
A rule specifies which events go to which targets on a bus; one rule fans out to multiple targets in parallel. The two types: rules that match on event data (event patterns) and rules that run on a schedule — the scheduled kind is now legacy, succeeded by EventBridge Scheduler.

2. The classic-bus numbers to quote?

Show answer
300 rules per event bus (adjustable), 5 targets per rule (not adjustable), 2,048-character event patterns, 100 event buses per account, custom/partner events $1.00 per million ingest in 64-KB chunks.

3. Which event JSON fields does PutEvents require — and what is the id for?

Show answer
source, detail-type and detail (a JSON object). The id UUID exists to trace events as they move through rules to targets.

4. Describe the classic cron shape and its quirks.

Show answer
Six fields: minutes hours day-of-month month day-of-week year; never * in both day fields (? in one); L/W/# wildcards; nothing faster than 1 minute; examples run in UTC. Legacy — Scheduler is the modern replacement.

5. Why move a cron job from a scheduled rule to EventBridge Scheduler?

Show answer
Scheduler gives time zones (with automatic DST), one-time at() schedules, a flexible time window that disperses invocations for reliability, 60-second precision, a retry policy (max age 86,400 s, up to 185 attempts) and SQS DLQs — plus much higher scale quotas (10M schedules/Region).

6. What protects against losing failed rule deliveries?

Show answer
Attach a dead-letter queue to the target: EventBridge default-retries 185 times over 24 hours; after exhaustion events drop unless a DLQ holds them. DLQs must be standard SQS queues and carry RULE_ARN/TARGET_ARN/ERROR_CODE.

1. Prod alarms must reach email + a chat webhook the moment they flip to ALARM.

Show answer
A rule on the default bus matching aws.cloudwatch / CloudWatch Alarm State Change (state=ALARM) pointing at an SNS topic (email + chat subscribers; filter policies trim noise). Delivery of alarm events to EventBridge is guaranteed by AWS.

2. S3 uploads feed three consumers with wildly different speeds and retry needs.

Show answer
Enable EventBridge on the bucket; one rule (Object Created) fans out to three SQS queues — each drains at its own pace with its own retention, batching and DLQ. Need a fourth consumer later? Add a queue. 5-target cap hit? Insert an SNS topic.

3. The compliance team wants a report run every weekday at 9 a.m. Europe/Stockholm — DST-proof.

Show answer
EventBridge Scheduler: a cron-based schedule in that time zone (DST adjusts automatically), optional flexible time window to smooth load, target Lambda (templated) — one-time variants use at().

4. A SaaS partner must push webhooks into your event ecosystem.

Show answer
Partner event sources on a partner event bus — the routing then happens with the standard bus machinery; API destinations carry your events outward to external HTTPS endpoints instead.

5. Deliveries to a throttled Lambda keep failing silently.

Show answer
Check the rule’s retry policy (default 185 retries / 24 h) and attach a DLQ (standard SQS only); alarm on DLQ depth, then resend events from the DLQ after fixing the target.

6. Ten teams, one bus — the platform team is drowning in routing edits.

Show answer
Move to the new Custom Event Bus: share via AWS RAM (e.g. subscribe-only permission), let every team attach its own subscribers, keep retention + replay on the bus — the platform team stops writing routing for others; RevokeResource withdraws anyone.
