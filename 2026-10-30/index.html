Pluralsight: Understanding Amazon CloudFront Architecture (Pawan Puthran) — why content delivery networks exist, how CloudFront’s 750+ PoPs, regional edge caches and Origin Shield deliver, origins locked by OAC, distributions and cache behaviors routed by path pattern, edge compute from CloudFront Functions to Lambda@Edge to Connection Functions, and 2026 pricing including flat-rate plans.

Summary

  • Why a CDN exists — content served from a far-away origin crosses many physical network devices, and every hop adds latency; Amazon’s own research put the price at roughly 1% of sales per 100 ms of latency. A content delivery network is a geographically distributed group of servers that caches content close to the end user, routing each viewer to the nearest, healthy point of presence — for static and dynamic content alike.
  • CloudFront’s edge network (2026) — 750+ points of presence in 100+ cities across 50+ countries sitting inside the AWS network (peered with thousands of telecom carriers), plus 1,140+ embedded PoPs across 300+ cities deployed inside ISP networks themselves, plus 15 regional edge caches within AWS Regions between the PoPs and your origins. Pay per use, no long-term commitments or minimum fee — and in 2026, flat-rate plan options joined the bill.
  • What a request meets — DNS resolution lands on CloudFront’s authoritative DNS, which picks the best PoP (distance, latency); the viewer’s HTTP request then maps to the distribution via its Host header, matches a cache behavior by path pattern, and is answered from the edge cache — on a miss, from the regional edge cache, and before the origin, from the optional Origin Shield.
  • Origins and locking them down — an origin is where content lives: S3 or any HTTP backend (EC2, load balancers, API Gateway, MediaPackage). Multiple origins per distribution, origin groups with primary/secondary failover, and Origin Access Control (OAC) with its three signing behaviors so direct S3 URLs fail and S3 serves only the requests the distribution signs.
  • Edge compute and paying for it — CloudFront Functions (sub-millisecond JavaScript at viewer events, millions of requests/second) vs Lambda@Edge (Node.js/Python at all four events, up to 30 s, network and body access) vs the new Connection Functions in the mTLS handshake. Billing: pay-as-you-go with a monthly free tier (1 TB data transfer out, 10M requests, 2M CloudFront Functions invocations), the 2026 flat-rate plans (Free $0 · Pro $15 · Business $200 · Premium $1,000/month, no overage charges), or the Security Savings Bundle (up to 30% off with a one-year commitment).

Main concepts

What a CDN is
A content delivery network is a geographically distributed group of servers that caches content close to the end user. At multiple geolocations a CDN establishes points of presence (edge-server clusters); when a viewer requests content, the CDN directs the request to the nearest server, weighing factors like edge-server health and proximity. Result: minimal data-travel distance, less delay, fast delivery — and it works for both static (HTML/CSS/JS, images) and dynamic content.
The latency tax
The farther a site is hosted from its visitor, the longer data takes to traverse the many physical network devices between them. Amazon’s published research found every 100 ms of latency cost about 1% in sales — minor delays measurably hurt user experience, satisfaction, and revenue. Load time also drives how long users are willing to wait at all. This is the gap a CDN exists to close.
What a CDN buys you
Three standing benefits: performance — caching near users shortens request/response distance, speeding page loads, cutting bounce rates, lifting engagement; bandwidth relief — serving everything from the origin demands big bandwidth and compute there, while CDN caching and optimizations shrink that load; availability and reliability — content and requests spread across many locations soften the impact of a localized outage and keep service continuous.
Amazon CloudFront — the AWS CDN
CloudFront delivers content such as videos and APIs with low latency and high transfer speed, economically. It bills pay per use — no long-term commitments, no minimum fee. It integrates with the AWS global infrastructure (physical locations directly connected to it) and with services like S3 and Route 53, and its global edge network pairs with thousands of telecom carriers for connection to all major access networks.
Edge network scale (verified 2026-10-30)
Today’s figures from AWS: 750+ PoPs in 100+ cities across 50+ countries, situated within the AWS network and peering with ISP networks; 15 regional edge caches within AWS Regions, between origins and the PoPs; plus 1,140+ embedded PoPs across 300+ cities (North/South America, Europe, Asia, Oceania). Amazon keeps adding edge locations every year — the numbers in this course’s recording (600+) were the snapshot at recording time.
Embedded PoPs
A second kind of presence: like regular PoPs they deploy within the AWS network — embedded PoPs sit directly inside ISP networks, closest to the end viewers. That placement avoids capacity bottlenecks in congested networks before traffic ever reaches the AWS backbone, improving performance further.
Why requests ride the AWS backbone
The internet is a network of networks: an ordinary browser request hops through them, and each hop adds latency; degraded links degrade the experience, and the response may not even return over the same path it went out on — with bad actors sniffing along the way. With CloudFront, the viewer connects to the nearest PoP, which connects onward to AWS Regions over a fully redundant AWS backbone — layers of parallel fibers across the globe interfacing with tens of thousands of networks — for faster origin fetches and dynamic-content acceleration.
Security at the edge
Content, APIs, and whole applications are delivered over HTTPS using the latest TLS versions to encrypt viewer→CloudFront communication. Access can be restricted by signed URLs and signed cookies (token-authenticated viewers only) and by geo-restriction (exclude specific countries). Shield, WAF, and Route 53 co-reside at the AWS edge with CloudFront, forming a layered perimeter against network- and application-layer DDoS and other attacks.
Use cases
Four classroom staples: media streaming — reliably and cost-effectively deliver rich video/audio while cutting bandwidth cost, gaining scale, and shortening delivery time; high-speed whole-site delivery — static and dynamic content combined; multi-user scaling — a website origin manages only so many client connections, and CloudFront rapidly scales past that limit by taking load off the origin; API acceleration through its proxy mode.
Edge location vs regional edge cache
Edge locations are the worldwide data-center cache layer serving viewers with the lowest latency. Regional edge caches (RECs) are an additional caching layer within AWS Regions, between PoPs and origins — with a larger cache width than any individual edge location, so objects remain cached longer, keeping more content closer to viewers and reducing origin fetches. They are enabled by default for every distribution and add no additional charges.
The miss path: edge → REC → Origin Shield → origin
A viewer request lands at the nearest edge location. Found in cache — served. Not found → checked in the regional edge cache; found there — served from it to the viewer. Still missing → the request routes through the Origin Shield (if configured) and only then to the origin. Every layer is another place the answer can wait, closer than the origin.
Origin Shield
An optional centralized caching layer that raises the cache hit ratio and cuts redundant origin fetches: it checks its own central cache first, then makes consolidated origin fetches only for content it doesn’t already hold — collapsing requests across regions to as few as one request to the origin per object. In multi-CDN architectures CloudFront can act as the origin for other CDNs, with Origin Shield deduplicating their fetches. Best fit: viewers spread across many regions or origins doing expensive just-in-time processing (e.g. media packaging).
Origins
The source of your content: S3, or custom HTTP origins — EC2 instances, load balancers, API Gateway, Elemental MediaPackage, or any HTTP server. A distribution can define multiple origins (e.g., S3 for static images, API Gateway for API requests) with cache behaviors routing by path pattern. Origin groups pair a primary and a secondary origin with failover — targeted at availability.
VPC origins (new)
The distribution connects directly to origins living in a VPC private subnet — Application Load Balancers, Network Load Balancers, and EC2 instances — with no internet gateway or public IP on the origin path. For other CloudFront-to-origin security postures: origin mutual TLS or custom-header validation.
Origin Access Control (OAC)
The recommended way to protect an S3 origin (recommended over legacy OAI): restricts the bucket so objects are reachable only through designated CloudFront distributions — all direct URL access is denied. The S3 bucket policy permits the service principal cloudfront.amazonaws.com plus a Condition on the source distribution’s ARN (so even other distributions can’t piggyback). OAC supports SSE-KMS encryption, PUT/DELETE dynamic requests, and all AWS Regions including opt-in ones; S3 Object Ownership must be Bucket owner enforced (the default for new buckets).
OAC’s three signing behaviors
Sign requests (recommended; “always” in the API): CloudFront signs every origin request — its own Authorization header per SigV4, which S3 verifies before serving. Do not override authorization header: CloudFront signs only when the viewer request carries no Authorization header, otherwise the client’s own header passes through — the split where clients sign their own uploads to S3 while CloudFront signs reads (bucket policy must be configured accordingly). Do not sign requests: signing off entirely — only for a client that always signs, or a public bucket (which is not best practice).
Distributions
The main building block of CloudFront: a configuration that tells CloudFront where the content is (origins), how to route requests (cache behaviors), and how to handle the delivery aspects (protocols, protection, pricing scope). Each distribution gets a unique CloudFront domain name (d….cloudfront.net) to serve from; you can point your own domain at it via alternate domain names. Other CDNs call the same concept a configuration, property, or endpoint.
Distribution settings that matter
Key knobs when creating one: the origin domain (DNS name of the origin) and an origin ID/name that cache behaviors reference; origin access settings keeping S3 private; attaching AWS WAF to block bad requests before they reach the origin; the minimum SSL/TLS protocol and ciphers CloudFront may use toward viewers; and the price class limiting which edge locations may serve you (three classes, trading coverage for cost — default uses the whole network for best performance). Deploying takes a few minutes; custom error responses round out polish.
Cache behaviors
Each behavior describes how CloudFront processes a class of requests, matched by path pattern with wildcards (e.g. /images/*, /api/*). Each behavior binds exactly one origin — that’s how a distribution serves static images from S3 while API paths route to API Gateway. The default cache behavior is created automatically, acts as the catch-all for requests matching no other path pattern, and is always processed last.
The policy trio per behavior
Behaviors carry three policy types that tune caching correctness and hit ratio: the cache-key policy — which request attributes (headers, cookies, query strings, URL) define the cache key (narrower keys = better hit ratio); the origin request policy — which values get forwarded to the origin; and the response header policy — which HTTP headers CloudFront adds or modifies in the response to viewers. Lambda@Edge/CloudFront Functions attach per behavior for computations at the edge.
CloudFront Functions
Lightweight JavaScript for high-scale, latency-sensitive CDN tweaks: cache-key normalization, header manipulation, URL rewrites/redirects, request authorization (e.g., hashed tokens/JWTs). Run at viewer request and viewer response only; sub-millisecond startup; scale to millions of requests per second; caps: 2 MB memory, 10 KB code; no network, file-system, or request-body access — but geolocation and device data are available. A native feature: build, test, and deploy entirely within CloudFront. With the runtime 2.0, they read CloudFront KeyValueStore for shared edge data.
Lambda@Edge
The heavier tool: Node.js or Python functions for work that takes several milliseconds or more, needs adjustable CPU/memory or third-party libraries (incl. the AWS SDK), network access to external services, file-system or HTTP-body access. Runs at all four events — viewer request/response AND origin request/response; duration up to 30 s; memory 128 MB on viewer events and up to 10 GB on origin events; code up to 50 MB. You publish in one Region; associating with a distribution auto-replicates the code around the world. Scale ceiling: ~10,000 requests/s per Region.
Connection Functions (2026)
A third, native edge-compute option: lightweight JavaScript run during the mTLS connection handshake — validate client certificates, implement custom authentication logic, handle certificate revocation — before any HTTP processing even starts. Like CloudFront Functions, buildable/testable/deployable entirely within CloudFront.
Freshness: TTLs, invalidations
Default caching: if the origin sends no cache control header, each edge location re-checks for an updated object 24 hours after the last check (configurable TTLs exist). To pull objects from all edge locations before expiry, use the Invalidation API: per distribution you can keep invalidations for up to 3,000 objects in progress (any mix of requests), and with the wildcard * up to 15 paths in progress. Invalidation usage is outside the pay-as-you-go free tier and bills per path beyond the monthly allowance.
Paying for CloudFront (2026)
Two models coexist. Pay-as-you-go: data transfer and request fees, no minimums; monthly free tier of 1 TB data transfer out + 10,000,000 HTTP/HTTPS requests + 2,000,000 CloudFront Functions invocations — invalidations, proxy requests, Lambda@Edge, Origin Shield, and data transfer to origins all bill. Flat-rate plans: $0 Free (~1M requests + 100 GB transfer), $15 Pro, $200 Business, $1,000 Premium, custom on request — each bundles WAF/DDoS protection, Route 53 DNS, log ingestion, a TLS certificate, serverless edge compute and S3 storage credits, with no overage charges. A Security Savings Bundle (up to 30% off for a one-year monthly commitment; WAF usage up to 10% of the commitment included) spans the pay-as-you-go side; price classes shave delivery cost by excluding the most expensive edge locations.

Quizzes

1. What is a content delivery network, and which problem does it solve?

Show answer
A geographically distributed group of servers that caches content close to the end user. It solves distance-induced latency: without it, far users traverse many network devices and every hop adds delay (Amazon measured ~1% sales lost per 100 ms). The CDN directs each request to the nearest healthy edge server, for static and dynamic content.

2. What did Amazon quantify about latency, and why does it matter commercially?

Show answer
Amazon published that every 100 ms of latency cost about 1% in sales — even minor delays measurably affect user experience, satisfaction, and revenue. Load time also governs how long visitors wait at all.

3. Name the three caching layers CloudFront uses between the viewer and the origin — with today's scale figures.

Show answer
Edge locations (750+ PoPs in 100+ cities, 50+ countries), regional edge caches (15, inside AWS Regions, between PoPs and origins), and the optional Origin Shield (central cache in front of the origin). Plus 1,140+ embedded PoPs inside ISP networks.

4. Walk the request path for content missing at every cache layer.

Show answer
DNS lands on CloudFront's authoritative DNS, which picks the best PoP (distance/latency); the viewer's HTTP request maps to the distribution via the Host header; the path pattern picks the cache behavior and origin; the edge cache misses, the regional edge cache misses, then the request routes via Origin Shield to the origin; the response is cached at every layer on the way back.

5. What may serve as a CloudFront origin?

Show answer
S3, and custom origins: EC2 instances, load balancers, API Gateway, Elemental MediaPackage, or any HTTP server. Multiple origins per distribution, and origin groups (primary + secondary) for failover.

6. What is OAC for, and what does its S3 bucket policy look like?

Show answer
It restricts S3 so objects are served only through designated distributions — direct URLs are denied. The bucket policy allows the service principal cloudfront.amazonaws.com with a Condition on the distribution's AWS:SourceArn. OAC also requires S3 Object Ownership set to Bucket owner enforced.

7. Name OAC's three signing behaviors with a use case each.

Show answer
Sign requests (recommended): CloudFront signs everything — the standard locked-down S3 read pattern. Do not override authorization header: clients sign their own uploads while CloudFront signs reads. Do not sign requests: client always-signs setups or (not best practice) public buckets.

8. Distribution vs cache behavior — what does each decide?

Show answer
The distribution is the delivery unit: which origins exist, routing, protocol/security/pricing settings, and its cloudfront.net domain. A cache behavior inside it maps path patterns to one origin plus caching policies; the auto-created default behavior is the catch-all, processed last.

9. Header rewrite at millions of requests per second — CloudFront Functions or Lambda@Edge? And fetching data via the AWS SDK at the origin step?

Show answer
Header rewrite → CloudFront Functions: sub-millisecond, viewer events, millions req/s, 10 KB code. SDK/external-network work → Lambda@Edge: network + body access, up to 30 s, 50 MB code, origin events included.

10. Which free allowances does pay-as-you-go CloudFront carry per month — and what stays chargeable?

Show answer
1 TB data transfer out, 10,000,000 HTTP/HTTPS requests, 2,000,000 CloudFront Functions invocations. Chargeable beyond that: invalidations, proxy requests, Lambda@Edge, Origin Shield, and data transfer to origins.

1. A family-owned pie shop sells online and just went international; overseas visitors face slow pages while the single origin strains.

Show answer
Put the site behind CloudFront: content cached at the nearest PoP to every viewer; requests stop traversing half the internet; the origin sheds bandwidth and connection load; load time, bounce rate, and engagement all improve.

2. A video library sits in a public S3 bucket; links get copied around the web and bandwidth bills spike.

Show answer
Lock the bucket with OAC: bucket policy allows the cloudfront.amazonaws.com principal with the distribution's source-ARN condition; 'Sign requests' so CloudFront signs every fetch; direct URLs are denied — the bucket stops being public entirely.

3. A paid report must go to one buyer by time-limited download link; a member library's hundreds of files unlock after login.

Show answer
One-time restricted file → a signed URL. Many files behind one login → a signed cookie, so tokenization happens once, not per file.

4. One application serves product images from S3 and a booking API from API Gateway; static and API traffic share one distribution.

Show answer
Two cache behaviors: /images/* binds the S3 origin with image-tuned caching; /api/* binds the API Gateway origin (proxy mode acceleration). The default behavior catches whatever doesn't match — processed last.

5. You need to normalize cache keys and rewrite URLs on every request at very high, spiky scale — nothing heavier.

Show answer
CloudFront Functions: sub-millisecond startup, millions of requests/second, viewer-request event, no network access needed for URL/header/cache-key work. Cheaper and lighter than Lambda@Edge.

6. The origin needs requests enriched with AWS SDK calls and the full HTTP body examined before forwarding.

Show answer
Lambda@Edge on the origin request event: network access for external calls, request-body access, 50 MB code for libraries, up to 30 s. Replicated from one Region to every edge automatically.

7. A global streaming platform transcodes (just-in-time packaging) per request; viewers span every region and the origin keeps getting hammered.

Show answer
Origin Shield: the central cache absorbs redundant fetches — as few as one request per object to the origin, consolidated across regions; origin-side just-in-time packaging runs once instead of many times.

8. Flash-sale traffic would blow past the origin's connection limit in seconds.

Show answer
Multi-user scaling via CloudFront: the distribution manages viewer connections at the edge and keeps only the necessary origin fetches — the origin survives far beyond its own connection ceiling.
