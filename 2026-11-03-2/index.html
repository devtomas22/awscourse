Summary — round 2

Session 2 over the same transcript: the angles here go deeper where session 1 stayed flat — no repeat statements anywhere on this page.

  • One central place, two actions — services send data in predefined time increments into CloudWatch, which stores it as CloudWatch Metrics. From that single repository you create alarms, and you can create rules that action other services — telemetry monitoring's whole point: identify performance, detect and resolve issues, optimize workloads.
  • Namespace isolation is the real lesson of the hierarchy — namespace → dimensions → metrics. Docs ground it: there is no default namespace (you specify one per data point), AWS namespaces follow the AWS/service convention, and metrics in different namespaces are kept separate so applications never blend into the same statistics. Dimensions then scope the hunt: the demo filtered Per-Instance Metrics by the instance's Instance ID to land on exactly one CPUUtilization.
  • Granularity has consequences — basic monitoring is default and free at five-minute granularity, so an alarm on basic data evaluates five-minute data points; detailed monitoring is one-minute data, charged, for certain resource types (EC2 publishes one-minute intervals instead of five-minute basic ones — enhanced monitoring on Beanstalk, request metrics on S3). Production and troubleshooting are the stated use cases.
  • Where metrics live and die — they exist only in the Region they were created (a missing dashboard starts with a Region check), they cannot be deleted, and they expire after 15 months without new data.
  • The agent fills the in-guest gap — memory and page file usage sit inside the OS, outside default collection; the agent (one downloadable package across EC2, containers, on-premises servers — Amazon Linux 2023/2, Ubuntu, RHEL, SLES, Oracle, Alma, Rocky, macOS, Windows Server and client) collects those in-guest metrics and pulls configured logs into CloudWatch Logs. The wizard picks what to collect; Systems Manager installs it once and reuses the configuration file on other instances.
  • Logs: structure first, then economics — log events form a Log Stream; streams gather into a Log Group. Two classes: Standard (anomaly detection, Live Tail near real time, get-log-events/filter-log-events) and Infrequent Access — renamed Essentials in today's docs — with the classes differing only in ingestion costs; pick at creation, because a log group's class can’t be changed afterwards.
  • Logs turn into numbers — metric filters translate log data into a numerical CloudWatch Metric that can then be alarmed. Vended logs are predefined per service (CloudTrail API activity, RDS database logs, delivery configurable); custom logs are yours (agent, CLI PutLogEvents command, or the PutLogEvents API for bulk).
  • Alarms are a state machine — a brand-new alarm shows Insufficient data until enough five-minute data points arrive; OK means the threshold isn’t breached and nothing needs investigating; In alarm means the metric hit the configured value. The demo watched exactly this timeline: insufficient data → in alarm.
  • The notification path is prebuilt — SNS is already integrated into CloudWatch (no code): topic → register endpoint (email) → confirm subscription → alarm uses the topic. The demo’s Standard topic cloudwatchalarmtopic carried the email; the alarm ec2cpuutiliz (CPUUtilization > 10%, five-minute period) delivered one out of the last one data point greater than the threshold of 10.
  • Demo numbers to remember — quiet instance: CPUUtilization 23.92 → 0.253 over an hour; after sudo dnf install stress -y + sudo stress --cpu 1 on cloudwatchalarmtest (Amazon Linux t3.micro, no key pair): 18.395 → alarm In alarm under the Alarms → In alarm filtered view.

Main concepts — round 2

Why a central repository matters
Everything CloudWatch does leans on one funnel: services push metric data in predefined increments into CloudWatch Metrics. Because it’s central, alarms can be created from any of it — and rules can action other services automatically. The dashboard is not the point; the reaction automation is.
Namespace isolation and naming
No default namespace exists — each data point names one — and AWS namespaces follow AWS/service (AWS/EC2). Isolation is the design intent: metrics of the same name from different namespaces never merge into the same statistics, so one app’s CPU never contaminates another’s.
Dimensions scope the hunt
Under AWS/EC2 sits the Per-Instance Metrics dimension; the demo added a filter on the Instance ID dimension to reduce the metric list to one instance, then picked CPUUtilization. Per-instance metric examples: Networking, CPU Credit Balance, CPUUtilization, EBS Read Bytes, EBS Write Bytes.
Granularity consequences: five minutes free, one minute paid
Basic = default, free, five-minute — meaning alarms evaluate on five-minute data points. Detailed = one-minute, charged, certain resource types; use for production workloads or troubleshooting. Names drift per service: EC2 detailed monitoring, Beanstalk enhanced monitoring, S3 request metrics.
Region-bound and self-expiring
Metrics exist only in the Region where they were created — the Region picker is step one of any “missing metric” hunt. They can’t be deleted; they auto-expire after 15 months without new data (rolling). History therefore exists — but only where and as long as the data supports it.
The in-guest gap and the agent
Default sets miss what lives inside the guest OS — memory and page file usage. The CloudWatch agent (downloadable package) covers EC2, containers, on-premises across a wide OS list (Amazon Linux 2023/2, Ubuntu, RHEL, SLES, Oracle, Alma, Rocky, macOS, Windows Server/client) and collects in-guest metrics plus configured logs.
Install it once with Systems Manager
Two install paths: manual CLI, or AWS Systems Manager — configure the agent once and reuse the configuration file on other EC2 instances (also valid for on-premises servers). The wizard is the guided way to choose the metrics — and which logs to pull into CloudWatch Logs.
Log streams and log groups in the console
The log events sent are a Log Stream; streams gather into a Log Group. That shape is what you navigate: group for configuration, stream for the timeline of events. CloudWatch Logs exists to centralize cloud-resource log files and enable log searches for insight.
Class economics: Standard vs Infrequent Access (Essentials)
Standard: full features — anomaly detection, Live Tail, get-log-events/filter-log-events. Infrequent Access: basic feature subset, for logs queried rarely. Today’s docs: renamed Essentials (formerly Infrequent Access; applies from December 2026 to API responses), classes differ only in ingestion costs (same storage and insights charges), and a log group’s class is fixed at creation.
Metric filters: logs → numbers → actions
A metric filter translates log data into a numerical CloudWatch Metric — e.g. the count of ERROR lines — and that metric can itself be actioned (alarmed). It’s the bridge between the Logs world and the Metrics world.
Vended vs custom: who owns the shape
Vended: enabled through an AWS service, predefined for that service — CloudTrail API activity, RDS database logs — though delivery into CloudWatch Logs may need configuring. Custom: managed and configured by you — typically application/system-level logging via the agent, or the PutLogEvents CLI command and API.
The three send-paths for custom logs
1) CloudWatch agent; 2) AWS CLI with the PutLogEvents command; 3) the PutLogEvents API — programmatic bulk upload. Agent = standing collection; CLI = quick manual pushes; API = your code uploading event batches.
The alarm state machine
Insufficient data: the fresh alarm hasn’t collected enough data points to determine okay vs breached — what the demo alarm showed first. OK: not within the threshold — nothing to investigate (the desired steady state). In alarm: the metric hit the configured value. Alarms move through these states as data points arrive.
SNS wiring order (no code required)
Create the topic → register the endpoint (an email address) with it → confirm the subscription from the inbox → configure the alarm to notify the topic. SNS is already integrated into CloudWatch — push notifications to registered endpoints need no custom code.
The demo timeline in numbers
cloudwatchalarmtest (Amazon Linux, t3.micro, no key pair) → Standard topic cloudwatchalarmtopic + Email subscription confirmed → EC2 Instance Connect: sudo dnf install stress -y → console: All metrics → EC2 → Per-Instance Metrics → Instance ID filter → CPUUtilization (23.92 → 0.253 over an hour) → Create alarm (button or chart bell; metric pre-populated): five-minute period, > 10%, existing topic, name ec2cpuutiliz → Insufficient data → sudo stress --cpu 1 → 18.395 → In alarm (Alarms → In alarm view) → email: one out of the last one data point greater than the threshold of 10.
The course’s practice tip
Cloud Sandboxes if your subscription includes them, otherwise a free account — and delete everything once you finish. One-off test resources (like the demo instance) are exactly what to clean up.

Quizzes — round 2

1. In the demo, where exactly was the CPUUtilization metric found in the console hierarchy?

Show answer
CloudWatch → Metrics → All metrics → the EC2 namespace → Per-Instance Metrics dimension → filtered by the instance’s Instance ID → CPUUtilization (23.92 → 0.253 over the hour).

2. Why did the brand-new alarm sit in Insufficient data — and what ended it?

Show answer
Not enough data collected yet to determine whether the metric is okay or breached. It ended once enough five-minute data points had arrived for the alarm to evaluate — the demo refreshed and waited.

3. What did the SNS email say when the alarm fired?

Show answer
Alarm ec2cpuutiliz: threshold crossed — one out of the last one data point greater than the threshold of 10. Delivered by SNS to the confirmed email endpoint.

4. Why did the demo alarm need no agent at all?

Show answer
CPUUtilization is part of the default basic set (five-minute, free) — the agent is only required for in-guest metrics like memory and page file usage that default monitoring can’t see.

5. Which numbers shaped the demo’s evaluation?

Show answer
Period: five minutes; threshold: greater than 10%; readings: 23.92 → 0.253 before load and 18.395 after stress --cpu 1 — the breach that flipped the alarm.

6. One log file is queried weekly by dashboards; another only after incidents. Class choice for each — and the catch?

Show answer
Weekly-queried → Standard (full features). Incident-only → Infrequent Access (Essentials in today’s docs) — cheaper ingestion, basic features. Catch: the class can’t be changed after the log group exists.

1. An app owner wants sub-five-minute detection but hasn’t enabled anything. What do you tell them about basic monitoring?

Show answer
Basic data is five-minute granularity — detection and alarm evaluation ride five-minute data points. For one-minute data enable detailed monitoring: charged, certain resource types (EC2 supports it).

2. You inherit 30 instances that all need the agent. How do you avoid 30 manual installs?

Show answer
Systems Manager: configure the agent once and reuse the configuration file to install on the other instances (it also covers on-premises servers). The manual path is the CLI.

3. A team rarely queries last year’s logs and wants the lowest cost — and asks to switch the class later if needs change. The catch?

Show answer
Infrequent Access (today’s Essentials) fits the access pattern — basic features, cheaper ingestion. Catch: the class is fixed at creation — no later switch (docs), so decide deliberately.

4. A repeating “ERROR” pattern in logs would be more useful as a trend line. Build it.

Show answer
A metric filter: it translates the log data into a numerical CloudWatch Metric, which you can then alarm and graph like any metric — logs feeding the metrics world.

5. A dashboard shows nothing for a metric created this morning “in another Region”. First check?

Show answer
The Region — metrics exist only in the Region where they were created. Then the usual trio (correct account → correct Region → IAM permission) explains most vanishings.

6. You want the alarm’s email to actually arrive. What’s the wiring order?

Show answer
SNS topic → register the Email endpoint → confirm the subscription from the inbox → configure the alarm to notify the topic. Skip the confirmation and the path silently dead-ends.
